# План: Единая функция переякорения владельца (вместо трёх копий) — «Смена прокладки»

> **Дата создания:** 2026-08-30  
> **Статус:** Зафиксирован как follow-up, НЕ входит в объём `PLAN_SHALLOW_TRANSFER_DND.md`  
> **Цель:** Вынести приём «переякорить осиротевших через сумму `ownerGap`, иначе — сирота-якорь на своём уровне» в одну переиспользуемую функцию в `hierarchy.js`, вместо того чтобы он был списан вручную в четырёх местах `reducer.js`.

## 0. Откуда взялась задача

Обнаружено при независимой проверке (Claude) премортема `PREMORTEM_SHALLOW_TRANSFER_DND.md` по реальному коду — см. `PLAN_SHALLOW_TRANSFER_DND.md`, раздел 5 («Возможное улучшение на будущее»). Приём переякорения — самая математически рискованная часть системы уровней (риск 1 в премортеме) — уже реализован и обкатан тестами, но **независимо, три раза подряд**, слегка отличающимися друг от друга копиями. С приходом «переноса без веток» (`PLAN_SHALLOW_TRANSFER_DND.md`) появится **четвёртая** такая копия.

Аналогия: четыре крана, в каждом своя резиновая прокладка, вырезанная вручную «на глаз» под конкретный кран. Работают одинаково, но это четыре разных прокладки. Если в приёме найдётся баг, чинить его придётся в четырёх местах — и легко забыть одно.

## 1. Где сейчас живут копии приёма (по факту, в `app/store/reducer.js`)

| # | Место | Экшен(ы) | Особенность именно этой копии |
|---|---|---|---|
| 1 | `applyRemoveLevelWindow` (~строка 1055–1118, `gapOf`/`withGap`/`reanchor` ~1067–1118) | `REMOVE_LEVEL_WINDOW`, `REMOVE_ROOT_CANVAS` | Уровень целиком исчезает — дистанция дополнительно уменьшается на 1 (`gapOf(e) + gapOf(deadOwner) - 1`), плюс отдельная ветка для тех, у кого предок жив, но связь «перепрыгивала» удаляемый уровень (тоже `-1`), плюс сдвиг `homeLevel` и `parentId → 'root'` |
| 2 | `case 'DELETE_SELECTED'` (~строка 2420–2560, `gapOf`/`withGap`/`reanchor` ~2480–2513) | `DELETE_SELECTED` (каскадное удаление узлов/слоёв, Delete на выделении) | Уровни не сдвигаются (удалённые сущности произвольно разбросаны по уровням, не один сплошной уровень) — только сумма дистанций и откат в сироту |
| 3 | `case 'CLEAR_LEVEL_WINDOW'` (~строка 2938–3010, `gapOf`/`withGap`/`reanchor` ~2956–2998) | `CLEAR_LEVEL_WINDOW` | Уровень не исчезает, только опустошается — по форме почти идентична копии №2, но набор удаляемых id — «все на одном конкретном уровне», а не «выделенные плюс их потомки» |
| 4 | *(появится)* `case 'TRANSFER_NODE'`, режим `'shallow'` | `TRANSFER_NODE` | См. `PLAN_SHALLOW_TRANSFER_DND.md`. Уровень не сдвигается (как №2/№3), но нужен доп. параметр: не отвязывать подопечного, если он сам есть в переносимом наборе `ids` (риск 2 премортема — уникально для этого места) |

Общий скелет во всех трёх существующих копиях один и тот же:

```
gapOf(e)   — дистанция сущности до владельца (по умолчанию 1)
withGap(e, gap) — записать дистанцию, если > 1, иначе убрать поле
reanchor(entity):
    если владелец удалён/уехал:
        подниматься по цепочке ownerId, суммируя дистанции,
        пока не найдётся живой предок
        если нашёлся — ownerId = предок, gap = сумма
        если нет — ownerId = null, homeLevel = свой текущий уровень
```

---

## 2. Что предлагается сделать

Вынести этот скелет в `app/utils/hierarchy.js` (там уже лежат все правила родства — `getOwnerGap`, `getLevel`, `hasAncestorIn` и т.д.) одной функцией, например:

```js
HierarchyUtils.reanchorSurvivor(entity, {
    isRemoved,      // (id) => bool — сущность-владелец считается «пропавшей»
    getEntity,      // (id) => node|layer|undefined
    getOwnLevel,    // (id) => number — для homeLevel сироты
    levelShift = 0, // на сколько сдвинуть homeLevel/уровень (нужно только REMOVE_LEVEL_WINDOW)
    skipReanchor    // необязательно: (id) => bool — не трогать эту сущность (риск 2 из TRANSFER_NODE)
})
```

Каждое из четырёх мест вызывает эту функцию, передавая свой набор «пропавших» id и свои мелкие особенности через параметры — вместо того чтобы держать собственную копию `gapOf`/`withGap`/`reanchor`.

**Важно:** если различия между местами (особенно у `REMOVE_LEVEL_WINDOW` со сдвигом уровня) окажутся слишком запутанными для одной функции с флагами — лучше оставить чуть больше параметров, чем прятать три разных поведения в одном труднопонятном `if`. Единообразие не важнее читаемости.

## 4. Риски и как их держать под контролем

- **Главный риск — не в новой логике, а в пересадке уже работающей.** Три места уже проходят тесты сегодня; при переносе легко случайно чуть-чуть изменить редкий крайний случай (например, порядок сложения `levelShift` и суммы гэпов в `applyRemoveLevelWindow`). Защита: переключать по одному месту за раз, отдельным шагом/коммитом, с полным прогоном тестов между шагами — не переключать все три сразу одним махом.
- **Риск переусложнить функцию флагами.** Если ради унификации функция обрастёт большим количеством `if (opts.xxx)`, читать её станет труднее, чем три отдельные копии. Если в процессе станет видно, что общего меньше, чем казалось — не насиловать унификацию, оставить как есть.

## 5. Когда делать

Рекомендуется **после** того, как `PLAN_SHALLOW_TRANSFER_DND.md` выкатится и обкатается в работе — чтобы не смешивать риск новой фичи (перенос без веток) с риском рефакторинга старого, уже работающего кода. Это самостоятельная задача, не блокирующая перенос без веток.
