   меню. Плюс **новая** кнопка «Добавить проект» — создаёт с нуля второй

9. **Судьба оставшихся кнопок тулбара** — решено:

     из интерфейса полностью, никуда не переносится.
   - «Выровнять слои» (`ALIGN_LAYERS`) — переезжает из тулбара в панель
     свойств уровня (то, что открывается кликом по шапке окна уровня,
     `ContextActionBar.js`, ветка `level-window-*`).
   - «Изоляция» (`icon-scan`) — переезжает под кнопку «+» (отдельная кнопка

     условие, по которому кнопка сейчас включается/выключается, просто
     теперь ещё и определяет её видимость, а не только состояние.
   - Индикатор зума — переезжает в правый верхний угол экрана, фиксированной
     позицией (`fixed top-4 right-4` или похоже), вне вертикального дока.

## 1. Почему это «узкое место» (архитектурная причина)

Всё состояние приложения — это **один плоский объект** в одном
`useReducer` (`Store.js`), с одним ключом в `localStorage`. Все поля —
синглтон на всё приложение, не на проект:

```
state = {
  nodes: {...}, layers: {...}, ports: {...}, links: {...},
  levelWindows: {...},              // окна уровней — одно дерево на всех
  projectName, projectColor, projectFontFamily, projectContent,
  selectedIds, isolatedIds, canvas: {offset, zoom},
  past: [...], future: [...],       // история — одна на всё
  ui: {...}
}
```

Важно: текущая модель устроена так, что **проект существует всегда** —
`getInitialState()` создаёт уровень 0 («Главный холст») сразу при первом
запуске, и убрать этот единственный уровень из UI сейчас нельзя в принципе
(кнопки уровня «удалить Главный холст» нет — есть только «удалить
дополнительный уровень» и «очистить содержимое»). Поэтому пункты 5–6
вашего уточнения («удалить проект целиком, включая единственный, до
полностью пустого холста») невозможны без изменения модели данных — это
не баг, а прямое следствие того, что в текущей архитектуре «нет проекта»
просто не предусмотренное состояние.

Плашка на холсте (`Canvas.js`) — это не компонент с собственными данными,
а фиксированный `<div>`, который читает `state.projectName` напрямую.
Панель свойств открывается по условию `selectedIds[0] === 'project'` — тоже
единственная в своём роде, второй такой быть не может.

Импорт (`Toolbar.js: handleImport`) не «добавляет» проект — он вызывает
`LOAD_STATE`, который **целиком заменяет** `nodes/layers/ports/links/...`.

Вся геометрия (`HierarchyUtils.getLocalPosition`, `GeometryUtils.
resolveLayerCollision`, вычисление уровня сущности по `parentId`/`ownerId`)
работает в одном плоском ID-пространстве без понятия «проект».

**Вывод:** пункты 1–4 (кнопки, тулбар) — точечные правки в текущей модели.
Пункты 5–8 (удаление проекта до пустоты, стартовый пустой холст, кнопка
«Добавить проект», гейтинг радиального меню) **все вместе требуют** ввести
в состояние понятие «проект» как отдельную сущность, которой может не быть
вообще ни одной. Это одна связная работа — искусственно её не разделить.

### Диагностика: «сброс к начальному состоянию не происходит»

Проверил напрямую через `reducer.js` (воспроизвёл на чистом состоянии с
несколькими уровнями, минуя UI — так виднее, что делает именно редьюсер, а
не что-то в рендере). Два разных явления, у них разная природа:

**1. Это баг, чинится сейчас, без мультипроекта.** Кнопка-корзина в панели
свойств проекта («Очистить проект и сбросить к начальному состоянию»)
диспатчит `CLEAR_PROJECT`. Проверка показала:

```
до:    levelWindows: [0, 1]        (два окна уровня)
после: levelWindows: [0, 1]        (те же два — ничего не удалилось!)
       nodes: []                    (содержимое стёрто)
```

`CLEAR_PROJECT` действительно чистит `nodes/layers/links` до `{}` (это
работает), но **окна уровней (`levelWindows`) не трогает вообще** — это
намеренное поведение из старой версии (см. комментарий в самом reducer.js:
«окна и настройки проекта сохраняются»), которое **противоречит собственной
подписи кнопки** («...сбросить к начальному состоянию»). Начальное
состояние — это ОДИН уровень (Главный холст), а не N пустых рамок. Именно
эта лишняя пустая рамка уровня 1 (и любого другого, что был до очистки) и
есть тот «зависший уровень», который вы видите на холсте после нажатия
корзины — он не удаляется, потому что редьюсер его и не пытается удалить.
Это никак не связано с мультипроектностью — исправление ниже (Этап 0.10)
работает на сегодняшней однопроектной модели, чинится независимо и сразу.

**2. Это НЕ баг, а именно то ограничение архитектуры, из-за которого весь
этот план и появился.** Когда уровней остаётся только один (Главный холст,
уровень 0) — ни кнопка «Удалить уровень» в панели свойств окна (она вообще
не показывается для уровня 0 — вместо неё «Удалить холст»), ни «Удалить
холст» сам по себе не могут удалить последний оставшийся уровень:

```js
// applyRemoveLevelWindow, reducer.js:703
if (removedLevel === 0 && !Object.values(state.levelWindows).some(w => w.levelIndex === 1)) {
    return state; // no-op: холст удалить нельзя, если некому занять его место
}
```

Проверил напрямую — при единственном уровне 0 `REMOVE_ROOT_CANVAS`
возвращает СТАРОЕ состояние без изменений (буквально `state === newState`).
Это сделано намеренно: текущая модель требует, чтобы хотя бы один уровень
существовал всегда (это и есть «проект» в сегодняшней архитектуре, см.
раздел 1). Полностью убрать даже единственный уровень — то есть получить
по-настоящему пустой холст без единой плашки — возможно только после
Этапа 1 (модель «ноль проектов», уже описана в разделе 3.6). Пока Этап 1 не
реализован, «сброс к начальному состоянию» технически может означать
максимум «остался ровно один пустой уровень 0» — не «нет уровней вообще».
Фикс ниже (0.10) добивается именно этого — большего в сегодняшней
архитектуре не сделать, не забегая вперёд Этапа 1.

### 0.10. Фикс: `CLEAR_PROJECT` должен по-настоящему сбрасывать до уровня 0

Меняю реализацию `CLEAR_PROJECT` в `reducer.js`: вместо очистки сущностей
с сохранением ВСЕХ `levelWindows`, оставляем только окно уровня 0 (его
имя/цвет/шрифт/камера — сохраняются, как и раньше), все остальные окна
уровней удаляются целиком вместе с их пер-уровневыми настройками:

```js
case 'CLEAR_PROJECT': {
    const historyState = saveHistory(state, 'Удаление проекта (сброс к начальному состоянию)');
    const rootWin = Object.values(state.levelWindows || {}).find(w => w && w.levelIndex === 0);
    return {
        ...state,
        ...historyState,
        nodes: {},
        layers: {},
        ports: {},   // мастер-порты тоже чистятся — вы подтвердили это раньше
        links: {},
        levelWindows: rootWin ? { [rootWin.id]: rootWin } : state.levelWindows,
        levelViews: rootWin ? { [rootWin.id]: state.levelViews?.[rootWin.id] } : {},
        levelFocusParentId: {},
        levelHideNeighbors: {},
        activeLevelIndex: 0,
        selectedIds: [],
        isolatedIds: []
    };
}
```

Реанкор (пере-якорение выживших потомков) здесь не нужен, в отличие от
`applyRemoveLevelWindow` — все сущности всё равно стираются, якорить
некого. Так кнопка-корзина в панели проекта наконец делает то, что
написано у неё в подсказке: после клика на холсте остаётся ровно один
пустой уровень 0 — визуально то же самое, что при первом запуске
приложения. Заодно закрывает более раннюю мою правку (было: «сохраняем
мастер-порты» — по вашему уточнению чистим и их).

Тесты: `tests/reducer.test.js` почти наверняка содержит кейсы на
`CLEAR_PROJECT` под старое поведение (сохранение окон) — их нужно
переписать под новое.

### Обновление радиального меню: 4 сателлита вместо 3

Решено (см. вопрос №0 в разделе 6): «Добавить проект» в меню пока не
показываем вообще — до Этапа 1 кнопка не может ничего реально сделать,
а дизейбленная кнопка-обещание создаёт больше вопросов, чем пользы.
Значит дуга вокруг «+» получает только одну новую позицию — «Создать
новый уровень». Геометрию `-60°/0°/+60°` (3 точки) пересчитываю под 4:
равномерно на дуге `-70°…+70°`, шаг ~47°: `-70°, -23°, +23°, +70°`.

Добавить ассистента. Когда дойдёт дело до Этапа 1, «Добавить проект»
добавится пятой точкой, и дугу придётся пересчитать ещё раз под 5 — на

сателлитов), закладывать «место про запас» заранее не вижу смысла.

## 3. Этап 1 — мультипроектность: модель данных (включая «ноль проектов»)

> **ЧАСТЬ 2 РЕАЛИЗОВАНА** (CHANGELOG 2026-08-23 (6)): стек плашек всех
> проектов, окна неактивных проектов видны на общем холсте (read-only,
> клик активирует), «Добавить проект» — 5-й сателлит меню «+», импорт
> добавляет проект (не заменяет), корзина = полное удаление проекта,
> несколько обозревателей одновременно, колонки окон по проектам.
> Этим Этапы 1–2 первоначального плана по сути закрыты; Этап 3
> (полировка: индикация, ручное перетаскивание плашек, лимиты) — по мере
> надобности после обкатки.
>
> **ЧАСТЬ 1 РЕАЛИЗОВАНА** (CHANGELOG 2026-08-23 (5)): модель v12
> (`projects`/`projectOrder`/`activeProjectId`), обёртка `multiReducer` над
> нетронутым внутренним редьюсером, миграция старых сохранений, раздельный
> Undo, «ноль проектов» как валидное состояние, экшены
> ADD/REMOVE/SET_ACTIVE_PROJECT, обозреватель под плашкой. Отличие от
> первоначального наброска: `canvas` (камера общего холста) — ГЛОБАЛЬНОЕ
> поле, не поле проекта (холст один на всех — решение «один общий
> бесконечный холст» делает камеру общей). UI мультипроекта (плашки всех
> проектов, «Добавить проект» в меню, импорт-как-добавление, переукладка
> плашек) — Часть 2, после проверки владельцем продукта, что регресса нет.
> Ещё одно решение владельца продукта: обозревателей может быть открыто
> НЕСКОЛЬКО одновременно (по одному на проект), панель встаёт под плашкой
> своего проекта, плашки остальных съезжают вниз — реализация в Части 2.

Ядро задачи. Затрагивает `reducer.js` (130 KB) и `Store.js`.

**3.1. Новая форма состояния**

```
state = {
  projects: {
    [projectId]: {
      nodes, layers, ports, links, levelWindows,
      projectName, projectColor, projectFontFamily, projectContent,
      selectedIds, isolatedIds, canvas: {offset, zoom},
      levelFocusParentId, levelHideNeighbors, activeLevelIndex,
      past, future, historyLogs,
      origin: { x, y }   // точка на общем холсте, где «стоит» плашка
    }
  },                                 // МОЖЕТ БЫТЬ ПУСТЫМ ОБЪЕКТОМ — валидное
                                     // состояние приложения (см. 3.6)
  projectOrder: [projectId, ...],   // порядок плашек; определяет пересчёт
                                     // `origin` при удалении одной из них
  activeProjectId: projectId | null,
  ui: {...}
}
```

**3.2. Совместимость и миграция**
- Старый формат `localStorage` (`architector_state_v10`, плоский,
  однопроектный) заворачивается при загрузке в `projects: {[newId]: <как
  есть>}`, `projectOrder: [newId]`, `activeProjectId: newId`, `origin:
  {x:0,y:0}`. Пишем как `formatVersion: 11`. Существующие пользователи не
  получают пустой холст после обновления — их текущий проект просто
  становится «первым» в новой модели.
- Экспорт `.json` не меняет формат — экспортируется один проект в прежней
  плоской форме (файлы старого формата остаются импортируемыми).

**3.3. Импорт = «добавить», а не «заменить»**
- Импорт из панели проекта — новый экшен `ADD_PROJECT_FROM_FILE`:
  генерирует новый `projectId`, ремапит id всех сущностей файла (включая
  ссылки `parentId/ownerId/nodeId/sourcePortId/targetPortId`), кладёт
  результат в `projects[newId]`, добавляет в `projectOrder`, ставит
  `origin` по следующему свободному слоту сетки авто-расстановки.

**3.4. «Добавить проект» с нуля**
- Новый экшен `ADD_PROJECT`: создаёт `projects[newId]` с ОДНИМ окном
  уровня 0, пустым содержимым, дефолтным именем «Проект N» (N — следующий
  порядковый номер, не считая удалённых, либо просто `Object.keys(projects
  ).length + 1` — уточню при реализации, чтобы не путать пользователя
  повторами номеров после удалений). Добавляет в `projectOrder`, назначает
  `activeProjectId = newId` (только что созданный проект сразу становится
  активным — логично, раз пользователь только что запросил в него
  добавление).

**3.5. «Удалить проект» — единая кнопка, полное удаление**
- Экшен `REMOVE_PROJECT { id }`: удаляет `projects[id]` целиком (все узлы,
  слои, порты, связи, окна уровней вместе с настройками — ничего не
  остаётся), убирает `id` из `projectOrder`.
- **Переукладка (reflow):** `origin` оставшихся проектов пересчитывается
  по их новой позиции в `projectOrder` — если удалили первый из двух,
  второй занимает освободившийся слот (как вы уточнили). Действует то же
  правило слотовой сетки, что и при авто-расстановке новых проектов (3.3).
- Если удаляемый был `activeProjectId` — активным становится следующий по
  `projectOrder`, либо предыдущий, если удалили последний в списке, либо
  `null`, если проектов больше не осталось.
- Подтверждение перед удалением — как сейчас (`window.confirm`), текст
  недвусмысленно предупреждает про полное удаление уровней:
  «Проект будет удалён полностью, включая все уровни и их содержимое.
  Продолжить?».
- Старый `CLEAR_PROJECT` (чистит содержимое, сохраняя пустые рамки уровней)
  как отдельное пользовательское действие **не нужен** — убираем его из UI.
  Как reducer-кейс можно оставить неиспользуемым (не помешает) или удалить
  вместе с обновлением тестов — решим при реализации, глядя, ссылается ли
  на него что-то ещё (например, ИИ-ассистент).

**3.6. Пустое состояние — стартовый экран**
- `getInitialState()` возвращает `projects: {}, projectOrder: [],
  activeProjectId: null` для НОВЫХ пользователей (нет сохранения в
  `localStorage`). Существующие сохранения мигрируют по правилу 3.2 и
  пустыми не становятся.
- `Canvas.js` при пустом `projects` не рендерит ни плашек, ни окон уровней —
  просто сетка холста. Единственный активный элемент интерфейса — кнопка
  «+» с доступной в её меню кнопкой «Добавить проект» (см. 4.2).
- Тот же экран получается, если пользователь удалил все проекты по одному —
  реализуется автоматически, если 3.5 и рендер в `Canvas.js` корректно
  обрабатывают `projects = {}`, отдельного кода «вернуться к пустому
  экрану» не требуется.

**Критерий готовности Этапа 1:** старые сохранения открываются без потери
данных как один (мигрированный) проект; новые пользователи видят пустой
холст; юнит-тесты на структуру состояния и на миграцию — зелёные
(по аналогии с `tests/migration.test.js`); UI ещё не переключён (Этап 2).

## 4. Этап 2 — адаптация UI под мультипроект (включая гейтинг)

**4.1. Общее правило переключения контекста**
Все компоненты, читавшие `state.X` напрямую, переходят на
`state.projects[state.activeProjectId]?.X` (с защитой на `activeProjectId
=== null`). `reducer.js` — через помощник `updateProject(state, projectId,
updater)`.

**4.2. Радиальное меню «+» — гейтинг и «Добавить проект»**
- Кнопка «Добавить проект» добавляется в дугу (4-й сателлит), диспатчит
  `ADD_PROJECT` (3.4), доступна ВСЕГДА, независимо от `addCtx`/наличия
  активного проекта — создание нового проекта никогда не требует
  выделения.
- Остальные 3 сателлита + сам «+» (узел): доступны, только если
  `activeProjectId !== null` И `addCtx.ok` (тот же флаг, что и сейчас, но
  вычисленный от `state.projects[activeProjectId]`, а не от корня
  `state`). Если `projects` пуст — `activeProjectId` гарантированно
  `null`, значит эти 4 кнопки задизейблены автоматически, без отдельного
  специального случая «холст совсем пуст» — это частный случай общего
  правила «нет активного проекта». Задизейбленные кнопки — с тем же
  паттерном, что сейчас у `addNode`/`addLayer` (`opacity-40 cursor-not-
  allowed`) и подсказкой «Сначала создайте проект» / текущей
  `addDisabledHint`, в зависимости от причины.

**4.3. Остальные модули**
- **`Canvas.js`** — рендерит `projectOrder.map(id => <ProjectPlate/>)`, у
  каждой — свой набор окон уровней от `origin`. Клик по плашке/окну
  выставляет `activeProjectId`.
- **`ContextActionBar.js`** — ветка проекта различает, чья именно плашка
  выбрана (`id === 'project:' + projectId`), показывает и применяет
  Импорт/Экспорт/Обозреватель/Удалить к этому конкретному проекту.
- **`OutlinerTree.js` / `Library.js`** — принимает `projectId` пропом,
  свой обозреватель на плашку (как решили ранее).
- **`HierarchyUtils` / `GeometryUtils`** — уже принимают под-стейт явными
  аргументами, менять сигнатуры, скорее всего, не придётся.

**Критерий готовности Этапа 2:** один проект на холсте работает
неотличимо от текущей версии; пустой холст (0 проектов) показывает только
активную кнопку «Добавить проект»; весь текущий набор тестов зелёный.

## 5. Этап 3 — полировка мультипроекта

- Авто-расстановка `origin` новых проектов не даёт плашкам/окнам
  накладываться друг на друга.
- Явная индикация активного проекта (подсветка плашки/рамки).
- Драг между уровнями/слоями РАЗНЫХ проектов — по умолчанию запрещён

- Проверка переукладки (3.5) на 3+ проектах, не только на кейсе «было
  два, осталось один».

**Критерий готовности Этапа 3:** можно создать/импортировать несколько
проектов с разным числом уровней, работать с каждым независимо (свои
плашка, обозреватель, импорт/экспорт, выравнивание окон, drag&drop,
удаление, панель свойств), удалить любой (включая последний, до полностью
пустого холста) и продолжить с «Добавить проект».
