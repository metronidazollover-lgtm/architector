## 0. Принятые решения

| Развилка | Решение |
|---|---|
| Модель хранения окна | **Окно = слой особого рода** в `state.layers` (`isLevelWindow: true`) плюс расщепление у узла: `parentId` = контейнер, `ownerId` = семантический родитель |
| Внутренняя панорама и зум окна | **Берём полностью:** у каждого окна свои `innerOffset` и `innerZoom`, содержимое обрезается рамкой окна |
| Пустое окно | **Удаляется автоматически**, когда в нём не осталось ни узлов, ни слоёв — **в том числе окно в середине цепочки** |
| Уровни после удаления | **Перенумеровываются:** все уровни ниже поднимаются на одно поколение вместе со всем содержимым |
| Точки-порты при внутреннем зуме | **Уменьшаются вместе с содержимым** (как сейчас ведёт себя общий зум холста) |
| Границы окна | **Наружу не выходит ничего.** Окно — полноценный холст в рамке (§4.0). Единственное исключение — межуровневые связи в глобальном слое |
| Межуровневые связи | **Через порты на рамках окон** (§4.4): три отрезка вместо одной линии. Прокси-порт связи вычисляется и не хранится |
| Связь с уровнем целиком | **Мастер-порт**: ровно один на окно, живёт на шапке, виден и в свёрнутом окне (§4.8) |
| Полукольца целевого уровня | **Сохраняются** и дублируются на прокси-порте рамки (§4.5) |
| Связь к прокси-порту | Прокси = ярлык дальнего порта: связь создаётся к представляемому порту (§4.6) |
| Порядок | Сначала доработка плана, код пока не трогаем |

Первоначально я рекомендовал отложить внутренний зум и клиппинг. Решение принято в пользу
полного варианта — **§3 и §4 ниже переписаны под него**: там точная математика
преобразований, перестройка рендера и честный список того, чем за это придётся заплатить.

## 1. Почему первая попытка «наломала дров»

План v1 описывает **что** должно получиться (это описано хорошо, и я это сохраняю),
но почти не описывает, **как это ложится на существующую модель данных**. Все 10 инцидентов

| Умолчание плана v1 | Какие инциденты породило |
|---|---|
| **A. Не определена система координат.** «Узлы внутри окна имеют относительные координаты к окну» — одна строка в таблице конфликтов. В реальности это отменяет инвариант v10 и ломает всю портовую и линковую геометрию. | 3 (стартовая точка связи), частично 1 |
| **B. `levelWindows` вынесен в отдельный словарь.** Он не попадает ни в снапшот истории (`reducer.js:277`), ни в экспорт (`Toolbar.js: handleExport`), ни в `LOAD_STATE`. | 1, плюс невидимые потери при Undo и экспорте, которые в отчёте даже не всплыли |
| **C. Не перечислены все места пересечения с существующим кодом.** Тулбар, изоляция, панель свойств, жесты — каждое всплыло уже в браузере. | 4, 5, 6, 9, 10 |
| **D. Не задан порядок работ.** Компоненты писались до того, как была готова геометрия, поэтому хуки и деструктуризация чинились по факту падения. | 7, 8 |

## 2. Что уже есть в коде (факты, а не предположения)

1. **Иерархия — одна ось: `parentId`.** Уровней в модели нет. Глубина вычисляется на лету:
   `HierarchyUtils.getEntityDepth` (`app/utils/hierarchy.js:102`). Слой **не увеличивает**
   глубину, узел-родитель — увеличивает.
2. **Координаты чисто аддитивные.** `getAbsolutePosition` (`app/utils/hierarchy.js:18`) —
   цикл `x += current.position.x` вверх по `parentId`. Никаких масштабов.
   Есть `WeakMap`-кэш, инвалидируемый по ссылке на `state.nodes`.
3. **Рендер плоский.** `Canvas.js` кладёт **все** слои, связи и узлы в один контейнер
   с `transform: translate(offset) scale(zoom)`. Узел — не DOM-потомок своего слоя,
   он абсолютно спозиционирован по мировым координатам. Вложенность — только математика.
4. **История хранит ровно 4 словаря:** `{layers, nodes, ports, links}` (`reducer.js:277`).
5. **Экспорт/импорт — те же 4 словаря плюс `canvas`.**
6. **Persist — на каждый dispatch.** `Store.js:9` делает `JSON.stringify(state)`
   в `useEffect([state])` — 60 раз в секунду при любом перетаскивании.
7. **Экран → мир считается в трёх местах независимо** (`Port.js` ×2, `PendingLink`
   в `Link.js`) по формуле `(clientX - rect.left - offset.x) / zoom`. Единой функции нет —
   поэтому инцидент 3 и был размазан по трём файлам.
8. **Геометрия слоёв агрессивна.** `resolveLayerCollisionsOnLoad`, `resolveContextCollisions`
   (отталкивание узлов от слоёв на 30px) и `getSmartPlacement` вызываются при `LOAD_STATE`
   и `ADD_NODE` (`reducer.js:326-347`, `reducer.js:452`).

### 2.1. Три бага, которые уже есть в чистой версии

Починить **до** начала работ, иначе всплывут посреди новой фичи и будут списаны на неё.

* **B1. `ADD_NODE` портит позицию соседей по слою.** `reducer.js:457` пишет
  `position: updatesById[nId]`, тогда как `getSmartPlacement` возвращает
  `{ parentId, position }`. В `LOAD_STATE` (`reducer.js:339`) та же строка написана верно.
  Итог: при добавлении узла в непустой слой соседи получают `position.x === undefined`
  и прыгают в угол слоя.
* **B2. Нарушение Rules of Hooks в `Link.js`.** Компонент делает `if (!data || …) return null;`
  **до** `useStore()`. Ровно тот класс дефекта, что дал инцидент 7 — пока не выстреливает
  только потому, что `Canvas` отфильтровывает битые связи заранее.
* **B3. Пунктир связей — мёртвая ветка.** `Link.js:187` читает `data.style === 'dashed'`,
  но поля `style` нет ни в модели, ни в AGENTS.md (там `linkStyle`), и **ничто в проекте
  его не выставляет** — проверено поиском по всей кодовой базе. Пунктир сейчас включить
  нечем, а весь показ межуровневых связей строится именно на нём.

## 3. Модель данных и математика координат

### 3.1. Сущности

```js
// Окно уровня — запись в state.layers
{
  id: 'lvlwin-7f3a',          // СТАБИЛЬНЫЙ id, НЕ содержит номер уровня
  isLevelWindow: true,        // дискриминатор
  levelIndex: 1,              // номер как ПОЛЕ, а не как ключ словаря
  name: 'Уровень 1',
  content: '', color: '#1e293b',
  position: { x, y },         // мировые координаты, parentId: 'root'
  size: { w, h },             // размер рамки на мировом холсте
  innerOffset: { x: 0, y: 0 },// панорама содержимого внутри рамки
  innerZoom: 1,               // собственный масштаб содержимого
  parentId: 'root'
}
```

```js
// Узел
{
  parentId: 'lvlwin-7f3a',    // КОНТЕЙНЕР: чья это система координат (окно | слой | узел)
  ownerId: 'node-A'           // СЕМАНТИКА: чей это «ребёнок» — бейдж 📁N, глаз, каскадное удаление
}
```

**Почему два поля, а не одно.** План v1 требует, чтобы в окне уровня 1 одновременно лежали
`А1, А2` (дети A) и `Б1, Б2` (дети Б). Оставим `parentId` семантическим (`node-A`) —
координаты `А1` потянутся от позиции `A` на уровне 0, и узлы разъедутся по миру вместо
того, чтобы лечь в окно. Сделаем `parentId` контейнером — развалится `getChildrenStats`
(бейдж `📁 N`), фильтр глаза и каскадное удаление. Два поля — единственный вариант
без скрытой рассинхронизации.

### 3.2. 🔑 Инвариант: окна не вкладываются друг в друга

Все окна уровней — прямые дети `root` и не могут лежать внутри других окон.

Это не косметическое ограничение, а **то, что делает внутренний зум вообще посильным**:
у любой сущности на пути к миру ровно **одна** граница масштаба — её собственное окно.
Если бы окна вкладывались, пришлось бы перемножать цепочку масштабов, и всё, что ниже,
усложнилось бы на порядок. Инвариант надо записать в `docs/ARCHITECTURE.md` и защитить
проверкой в `REPARENT_ENTITY`.

### 3.3. Формула преобразования

Для узла с локальной позицией `p` внутри окна `W` (возможно, через вложенные слои):

```
sum   = сумма position по цепочке parentId вверх ДО окна (не включая окно)
world = W.position + W.innerOffset + sum * W.innerZoom
scale = W.innerZoom
```

Для сущности вне окон (`parentId` доходит до `root`): `world = sum`, `scale = 1`.

Экранный масштаб сущности = `canvas.zoom * scale`.

Формула специально выбрана так, чтобы **точно совпадать с тем, что делает CSS**:
`transform: translate(innerOffset) scale(innerZoom)` на внутреннем контейнере окна даёт
ребёнку с `left/top = p` ровно `innerOffset + p * innerZoom`. Значит браузер и наши
вычисления не разойдутся — а расхождение между ними и есть инцидент 3 в его худшем виде.

### 3.4. Новое API в `hierarchy.js`

```js
HierarchyUtils.getWorldTransform(id, nodes, layers)   // → { x, y, scale }  ← ядро
HierarchyUtils.getAbsolutePosition(id, nodes, layers) // → { x, y }         ← обёртка, совместимость
HierarchyUtils.getOwningWindow(id, nodes, layers)     // → окно или null
HierarchyUtils.screenToWorld(clientX, clientY, canvas)
HierarchyUtils.worldToScreen(x, y, canvas)
HierarchyUtils.getPortWorldPosition(portId, state)    // единственная точка правды для портов
```

**Подводные камни ядра:**

* 🔴 **`WeakMap`-кэш в `getAbsolutePosition` завязан на ссылку `state.nodes`.** Теперь
  результат зависит ещё и от `innerOffset`/`innerZoom`, которые живут в `state.layers`.
  Кэш уже проверяет `generation.layersRef === layers` — это спасает, **но только если
  каждое изменение окна пересоздаёт объект `state.layers`**. Редьюсер обязан это гарантировать,
  и это надо покрыть тестом: изменил `innerZoom` → `getWorldTransform` вернул новое значение.
* 🔴 **`getAbsolutePosition` теряет информацию.** Любое место, которое возьмёт только `{x,y}`
  и потом умножит на `canvas.zoom`, промахнётся ровно в `innerZoom` раз. Правило: если
  дальше идёт умножение или деление на масштаб — вызывать **`getWorldTransform`**, а не обёртку.
* 🟡 Размер сущности в мире = `size * scale`. Это отдельная забытая величина: `CENTER_ON_ENTITY`
  и любые «вписать в экран» без неё дадут неверный зум.

### 3.5. Реестр мест, где сейчас делится или умножается на `zoom`

Каждое из них — потенциальный инцидент 3. Ни одно нельзя пропустить.

| Место | Что сейчас | Что должно стать |
|---|---|---|
| `Node.js` перетаскивание | `(clientX - startX) / zoom` | `/ (zoom * scale)` |
| `Node.js` ресайз | `(clientX - startX) / zoom` | `/ (zoom * scale)` |
| `Node.js` пороги `zoom < 0.4` (скрытие тела и портов) | `zoom` | `zoom * scale` — иначе окно, ужатое внутренним зумом, продолжит рисовать весь текст всех узлов |
| `Port.js` перетаскивание порта по периметру | ручной пересчёт через `offset/zoom` | **перевести на `getBoundingClientRect()` узла и работать в долях** — так масштаб вообще перестаёт участвовать |
| `Port.js` хит-тест «бросили связь на порт», радиус `30 / zoom` | мировые единицы | **считать в экранных координатах** — иначе в ужатом окне порты визуально в 15px друг от друга, а радиус останется 30 |
| `Port.js` хит-тест «бросили внутрь узла» | мировые координаты узла | `getWorldTransform` + `size * scale` |
| `Link.js` `PendingLink` | `(endPos - offset) / zoom` | `screenToWorld` + `getPortWorldPosition` |
| `Link.js` толщина линии | `strokeWidth: 2` | `vector-effect="non-scaling-stroke"` либо `2 / (zoom * scale)` — иначе одна и та же связь в разных окнах разной толщины |
| `reducer: CENTER_ON_ENTITY` | `size` в мире | `size * scale` |
| `Canvas.js` сетка `30 * zoom` | глобальная | внутри окна — `30 * zoom * innerZoom` |
| `Node.js` режим «добавить порт» | доли от `getBoundingClientRect` | **уже безопасно** — числитель и знаменатель масштабируются одинаково |
| `GeometryUtils` (раскладка, коллизии) | локальные координаты | **уже безопасно** — масштаб не участвует |

## 4. Перестройка рендера (следствие выбора «зум + клиппинг»)

### 4.0. 🔑 Правило: окно уровня — это полноценный холст

> Каждое окно уровня ведёт себя **ровно как обычный холст приложения**, только в рамке
> с шапкой и с собственным идентификатором. Внутри него — своя система координат, своя
> панорама, свой масштаб. Узлы, слои, порты и внутренние связи рисуются **внутри окна
> и наружу не выходят**. Само окно живёт в общей системе координат мирового холста.

Единственное исключение — **межуровневые связи**: по замыслу плана v1 (п.3.1) они точками
протягиваются через мировое пространство от окна к окну, поэтому рисуются в глобальном слое
поверх окон.

Это правило надо записать в `docs/ARCHITECTURE.md` — оно определяет и структуру рендера,
и то, каких взаимодействий у нас принципиально не будет (см. §4.3 про перенос узла между
уровнями).

### 4.1. Почему без неё нельзя

Сейчас узел рисуется так: `left: мировая_позиция; width: data.size.w`. Под масштабом окна
пришлось бы вручную умножать позицию, ширину, высоту, кегль шрифта, отступы, толщину рамок,
размер портов — и всё равно текст поехал бы иначе, чем в браузере.

CSS `transform: scale()` делает всё это правильно и бесплатно, но **только для DOM-потомков**.
Плюс `overflow: hidden` обрежет содержимое **только** если оно внутри окна по DOM.
Поэтому выбор «внутренний зум + обрезка» = обязательная перестройка `Canvas` из плоского
списка в дерево. Это самая крупная и самая рискованная часть работ.

### 4.2. Целевая структура

```
мировой контейнер          transform: translate(offset) scale(zoom)
├── окно уровня 0          left/top/width/height, overflow: hidden
│   ├── шапка окна         (вне масштабируемой области — иначе заголовок будет плясать)
│   └── вьюпорт            transform: translate(innerOffset) scale(innerZoom)
│       ├── слои и узлы    left/top в локальных координатах
│       └── svg            ВНУТРИуровневые связи, локальные координаты
├── окно уровня 1          …
└── svg глобальный         МЕЖуровневые связи, мировые координаты, поверх окон
```

### 4.3. Подводные камни перестройки — и цена, которую платим

* 🟢 **Обрезка принята как правило, а не как издержка.** Свечение выделения
  (`boxShadow: 0 0 40px`), обводка `outline-offset-[4px]` и наружные полукольца портов
  у узла возле самой рамки будут срезаны — и это ожидаемое поведение, а не дефект.
  Смягчение: небольшой внутренний отступ у окна, чтобы содержимое не подходило к рамке
  вплотную. Отдельный слой подсветки поверх окон **не делаем**.
* 🟢 **Перетаскивание узла из окна в окно жестом — не поддерживаем.** Это прямое следствие
  правила «наружу ничего не вылезает»: пока тащим, узел обрезался бы рамкой и визуально
  исчезал. Перенос на другой уровень — **команда**, а не жест: через панель свойств,
  дерево обозревателя (`OutlinerTree` уже умеет перевложение перетаскиванием внутри дерева)
  или вырезать/вставить. Это заодно снимает с фазы 4 «слой перетаскивания поверх окон»,
  который иначе пришлось бы городить.
* 🔴 **Связи расщепляются на два вида с разной системой координат.** Внутриуровневая —
  локальные координаты внутри окна, рисуется внутри окна и обрезается вместе с содержимым.
  Межуровневая — мировые координаты, в глобальном слое поверх окон.
  **Это единственное исключение из правила «наружу ничего не вылезает»**, и оно заложено
  в самом плане v1 (п.3.1: точечная линия «протягивается через мировое пространство»
  от окна к окну). Компонент `Link` придётся разделить или дать ему явный параметр
  пространства. Пограничный случай: связь становится межуровневой или перестаёт ею быть
  при переносе узла на другой уровень — компонент должен переехать из одного слоя в другой.
* 🔴 **Куда крепить межуровневую связь, если порт «уехал» за пределы видимой части окна?**
  При внутренней панораме порт может оказаться за рамкой. Тогда линия будет тянуться
  к невидимой точке. Нужно правило: обрезать линию по краю рамки окна и ставить там
  маркер направления. В плане v1 этого случая нет вообще.
* 🟡 **Перенос узла на другой уровень (командой)** = смена контейнера плюс пересчёт координат
  между двумя разными масштабами. `REPARENT_ENTITY` сейчас использует
  `getAbsolutePosition`/`toRelativePosition` — обе становятся масштабозависимыми.
* 🟡 **Производительность.** Каждое окно — свой слой композитинга. При панораме внутри окна
  меняется `transform` контейнера — это дёшево, **но** React перерисовывает все узлы при
  любом изменении состояния (в `Node` три `useMemo`, каждый пробегает по всем связям).
  `React.memo` на `Node`/`Link` и `will-change: transform` на вьюпорте окна становятся
  не пожеланием, а требованием.
* 🟡 **Шапка окна должна остаться вне масштабируемой области**, иначе при внутреннем зуме
  0.3 заголовок окна станет нечитаемым вместе с содержимым.

### 4.4. Порты на рамках окон и межуровневые связи

Межуровневая связь — единственное, что пересекает рамку, и она рисуется **тремя отрезками**.
Чтобы отрезки были осязаемыми, а не обрывками линии, каждый из них заканчивается
на **порте, живущем на рамке окна**.

**Межуровневая связь = три отрезка:**

1. порт узла → **прокси-порт** на рамке своего окна (внутри окна, обрезается вместе с содержимым);
2. прокси-порт → прокси-порт (в мировом пространстве, глобальный слой поверх окон);
3. прокси-порт на рамке целевого окна → порт узла (внутри целевого окна).

**У окна два вида портов, и их нельзя смешивать в одну сущность:**

| | **Прокси-порт связи** | **Мастер-порт уровня** |
|---|---|---|
| Сколько | по одному на каждую пересекающую рамку связь | **ровно один на окно**, всегда существует |
| Где | на рамке, в слоте ближайшей грани | **на шапке окна** (§4.8) |
| Откуда берётся | появляется сам, как только связь пересекает рамку | создаётся вместе с окном, вручную не создаётся и не удаляется |
| Хранится ли в состоянии | **нет** — производная от связи, вычисляется при рендере | да, запись в `state.ports` с `isMaster: true` |
| Что означает | проекция чужого порта на границу уровня | подключение к **уровню целиком** |
| Переименовать, покрасить | нет | да; удалить — нет |
| Undo / экспорт | не участвует (нечего терять) | участвует, как любой порт |

Прокси-порт не хранится намеренно: иначе он дублирует информацию, уже содержащуюся
в связи, и любое рассогласование между ними придётся ловить сверкой. Производная величина
рассинхронизироваться не может.

Мастер-порт, наоборот, хранится: связи ссылаются на порты по `id`, и половина кода делает
`state.ports[id]`. Хранимый мастер-порт работает во всей этой машинерии без исключений.
Цена — инвариант «у каждого окна ровно один мастер-порт» надо поддерживать: нормализатор
`ensureMasterPorts(state)` вызывается в `LOAD_STATE`, `UNDO`, `REDO` и миграции,
чтобы порт не потерялся при загрузке старого файла или откате истории.

**Почему отдельный мастер-порт лучше, чем «порты уровня где угодно на рамке»:**
исчезает конкуренция за место на грани между прокси и ручными портами, исчезает жест
создания и удаления, исчезает вопрос «к чему я подключаюсь — к узлу или к уровню»:
подключение к уровню имеет ровно один, всегда одинаково выглядящий адрес.

**Что это даёт по сравнению с «линия обрывается меткой на рамке»:**

* исчезает особый случай «порт уехал за рамку» — прокси-порт стоит на месте независимо
  от внутренней панорамы, а невидимым становится только внутренний отрезок;
* появляется точка навигации: клик по прокси-порту подводит панораму окна к дальнему концу связи;
* индикатор целевого уровня (полукольца, п.3.2 плана v1) **дублируется на прокси-порте** —
  там он всегда читаем, в отличие от порта узла (§4.5);
* бесплатно получается запрошенная возможность «подключить узел к целому уровню» —
  это просто связь, у которой один конец есть мастер-порт уровня.

**Подводные камни:**

* 🔴 **У порта появляется второй возможный владелец.** Сейчас `port.nodeId` всегда указывает
  в `state.nodes`. Мастер-порт указывает на окно, которое лежит в `state.layers`.
  Все места вида `state.nodes[port.nodeId]` начнут молча возвращать `undefined`:
  `Link.js`, `Port.js`, `Canvas.js`, `getPortAbs` и `CENTER_ON_ENTITY` в редьюсере,
  `DELETE_SELECTED` (удаление портов вместе с узлом), `getEntityDepth`, `ContextActionBar`.
  Нужен один резолвер `getPortOwner(portId, state) → { kind: 'node' | 'window', entity }`
  и перевод на него **всех** перечисленных мест — иначе получим россыпь тихих `undefined`.
* 🔴 **Порт на рамке не масштабируется внутренним зумом.** Он принадлежит рамке, а рамка —
  вне масштабируемой области (как и шапка окна, §4.3). Значит его мировая позиция считается
  напрямую из `win.position` и `win.size`, **минуя** `innerOffset`/`innerZoom`.
  Это отдельная ветка в `getPortWorldPosition`, и если её забыть, порты рамки поедут
  при первом же повороте колеса внутри окна.
* 🔴 **Порт на рамке рисуется вне обрезаемого контейнера.** Он сидит верхом на границе,
  поэтому внутри `overflow: hidden` у него срежется ровно половина. Слой портов рамки —
  рядом с шапкой окна, не внутри вьюпорта.
* 🔴 **Раскладка прокси-портов вдоль грани должна быть стабильной, а не геометрической.**
  Соблазн — ставить прокси туда, где связь пересекает рамку. Тогда при панораме внутри окна
  порты будут ползать по рамке, а при уходе узла из вида — слипаться в угол. Правильно:
  детерминированные слоты вдоль грани (сортировка по целевому уровню, затем по положению
  исходного порта), не зависящие от внутренней панорамы вовсе.
* 🟡 **Переполнение грани.** Двадцать связей вниз превратят нижнюю рамку в частокол.
  Нужно правило схлопывания: при нехватке слотов соседние прокси-порты объединяются
  в один с числом-бейджем, раскрывающимся по клику.
* 🟡 **Средний отрезок обязан начинаться и заканчиваться на рамке.** Провести одну прямую
  от порта до порта проще, но глобальный слой лежит выше окон и такая линия проляжет
  поверх чужого содержимого, нарушив §4.0.
* 🟡 **Все три отрезка считаются одной функцией.** Разведёшь вычисления по компонентам —
  получишь стык со сдвигом в пару пикселей на каждом изменении масштаба, то есть
  инцидент 3 в новом обличье.
* 🟡 **Оба порта в одном окне** — связь внутриуровневая, прокси-портов и глобального отрезка
  нет. Переход между режимами происходит при переносе узла на другой уровень (§4.3):
  компонент связи должен переехать из локального SVG в глобальный и обратно.
* 🟡 **Окна могут перекрываться** (план v1, п.5.1) — тогда средний отрезок может выродиться
  в нулевую длину. Прокси-порты рисуются всё равно, связь не должна пропадать бесследно.
* 🟡 **Удаление окна** удаляет и его мастер-порт, и все связи к нему — тем же экшеном,
  что и само окно (§7.1).
* 🟡 **Видимость пунктира на малом масштабе.** Точки `2 6` при общем масштабе меньше
  примерно 0.3 сливаются в пустоту. Нужен порог: ниже него связь рисуется тонкой сплошной
  линией, а не исчезает.

### 4.5. Полукольца целевого уровня: сохраняем и дублируем на рамке

Контур и наружные полукольца (план v1, п.3.2) остаются как основной индикатор того,
с каким уровнем установлена связь, и **рисуются дважды**: у порта узла и у прокси-порта
на рамке. Направление наружу сохраняется в обоих случаях: у порта узла — наружу от грани
узла, у порта рамки — наружу от грани окна.

**Уточнение к §4.0.** Правило «наружу ничего не вылезает» относится к **содержимому** окна.
Обвязка окна — шапка, рамка, порты рамки и их полукольца — принадлежит самой рамке
и может выходить за её габарит. Иначе прокси-порт срезался бы ровно пополам.
Это надо записать в `docs/ARCHITECTURE.md` вместе с §4.0, иначе два правила будут
противоречить друг другу.

**Почему дублирование полезно, а не избыточно:** полукольца на рамке живут вне
масштабируемой области, поэтому **читаются при любом внутреннем зуме** — даже когда
содержимое ужато до нечитаемого. А полукольца у порта узла возле границы окна всё равно
частично срежутся (§4.3) — теперь это не потеря информации, потому что тот же признак
продублирован на рамке.

**Подводные камни:**

* 🔴 **`Port.js` считает глубину не тем способом.** Текущий цикл `maxInternalDepth` идёт
  по `state.nodes[current.parentId]` и упрётся в окно (окно лежит в `layers`).
  Считать надо по `levelIndex` владеющих окон, через `getPortOwner` (§4.4).
* 🟡 **Нужно доопределить кодировку — в плане v1 она неполна.** Там «1-й уровень связи —
  контур, 2-й и далее — соответствующее число дуг», и связь с уровнем 0 не описана вовсе.
  Предлагаю: **замкнутый контур = у порта есть межуровневые связи; число наружных дуг =
  номер целевого уровня; для уровня 0 дуг нет, только контур.** Тогда шкала монотонна
  и совпадает с 0-based нумерацией уровней во всём остальном плане.
* 🟡 **Порт может иметь связи с несколькими разными уровнями.** Сейчас код берёт максимум.
  Решить явно: либо показывать самый глубокий уровень, либо рисовать дугу на каждый
  целевой уровень (радиус = номер уровня, пропуски осмысленны). Второе информативнее,
  первое проще. По умолчанию беру второе — но это стоит увидеть глазами на реальном графе.
* 🟡 **Предел читаемости.** Больше трёх-четырёх дуг сливаются в кашу. Нужен порог:
  дальше рисуется усечённый набор плюс цифра.
* 🟡 **Дуги не перехватывают мышь** — `pointer-events: none`, иначе они перекроют сам порт
  как цель для перетаскивания связи.

### 4.6. Что происходит при попытке подключить связь к прокси-порту

Прокси-порт выглядит как порт, значит пользователь неизбежно попробует на него бросить связь.
Молча игнорировать нельзя — это читается как «приложение подвисло».

**Базовое правило: прокси-порт — ярлык дальнего порта.** Бросок связи на прокси создаёт
связь с тем портом узла, который прокси представляет. То есть подключиться к узлу другого
уровня можно, не уходя на этот уровень. Перетаскивание **от** прокси симметрично: связь
начинается от представляемого порта.

Для этого вычисляемый прокси несёт в рантайме `representsPortId` и `linkId` — обе величины
известны по построению, хранить ничего не нужно.

**Правила и запреты:**

| Ситуация | Поведение |
|---|---|
| Бросок на прокси, представляющий один порт | Создаётся связь с этим портом |
| Бросок на **схлопнутый** прокси (несколько связей в одном слоте, §4.4) | Цель неоднозначна → слот не принимает связь, подсказка «раскройте слот» |
| Перетаскивание с прокси на прокси | Запрещено: хотя бы один конец должен быть настоящим портом — иначе пользователь вслепую соединяет два далёких узла |
| Прокси представляет порт того же узла, от которого тянут | Запрещено (самосоединение) |
| Такая связь уже есть | Вторая не создаётся, существующая подсвечивается |
| Бросок на **свободное место рамки или на шапку** (мимо прокси) | Связь идёт к **мастер-порту** уровня. Вся рамка работает как крупная мишень «подключить к этому уровню» |

**Подводные камни:**

* 🔴 **Хит-тест не увидит прокси.** `Port.js` при отпускании связи перебирает
  `Object.values(state.ports)` — прокси там нет, они вычисляемые. Нужен общий сборщик
  целей `getDropTargets(state)` = настоящие порты плюс вычисленные прокси, и `Port.js`
  переводится на него. Забыть это — значит получить порт, который выглядит кликабельным
  и молча не работает.
* 🔴 **Приоритет целей на рамке.** Порядок разбора: попали в радиус прокси-порта → он
  и есть цель; попали в мастер-порт → он; не попали ни во что → связь всё равно идёт
  к мастер-порту. Радиусы прокси не должны перекрываться, иначе бросок будет случайно
  «примагничиваться» к соседнему слоту.
* 🔴 **Умное создание порта расширяется, а не отключается.** Сейчас `Port.js` создаёт порт
  только при отпускании внутри узла. Теперь тот же жест работает и на рамке (мастер-порт),
  и на пустом холсте уровня (§12, вопрос 1). Логику выбора цели надо вынести
  в одну функцию `resolveDropTarget(point, state)` — иначе три ветки создания портов
  разъедутся по трём файлам, как разъехались три копии формулы координат.
* 🟡 **После создания связи слоты пересчитываются**, и прокси может переехать в соседний
  слот. Это не должно читаться как «промахнулся»: переезд анимировать, новую связь коротко
  подсветить.
* 🟡 **Подсказка при наведении.** Прокси обязан на ховере показывать, что он представляет:
  имя узла, имя порта и номер уровня. Иначе «ярлык» неотличим от настоящего порта,
  и пользователь будет удивляться, почему его нельзя переименовать.

### 4.7. Разбор сценария: порт со связями сразу к нескольким уровням

Ситуация: узел `А` на уровне 0, его потомки `А1` (ур. 1), `А2` (ур. 2), `А3` (ур. 3).
Сначала протянута связь `А1 ↔ А3`. Затем пользователь тянет связь от `А2`
и бросает её на прокси-порт, стоящий на рамке уровня 1.

**Шаг за шагом:**

1. Прокси на рамке уровня 1 представляет порт узла `А1` (§4.6) → создаётся связь
   **`А2 ↔ порт А1`**, а не связь с уровнем целиком. Чтобы получить связь с уровнем,
   надо бросить мимо прокси, на свободное место рамки — тогда связь пойдёт к мастер-порту.
2. У порта `А1` теперь **две** межуровневые связи: к уровню 3 и к уровню 2.
3. На рамке уровня 1 появляется **второй прокси**, в соседнем слоте: один представляет
   связь к уровню 3 (три контура), другой — к уровню 2 (два контура).
4. У порта `А2` появляется индикатор с одним контуром (цель — уровень 1),
   и на рамке уровня 2 — свой прокси с одним контуром.

**Что при этом надо доопределить — и почему это важно именно здесь:**

* 🔴 **Кольца на порте узла складываются в одно и то же.** При кодировке «столько контуров,
  сколько номер целевого уровня» набор `{2, 3}` заполняет те же слоты `1..3`, что и одна
  связь к уровню 3. То есть **вид порта `А1` после шага 1 не изменится** — по нему нельзя
  прочитать, что появилась вторая связь. Варианты:
  * **(а) Оставить как есть** — на порте узла кольца читаются как «докуда дотягивается
    самая дальняя связь», а точный состав виден на рамке, где у каждой связи свой прокси.
    Плюс подсказка при наведении со списком всех целей. *Рекомендую: не усложняет узел
    и опирается на дублирование, которое уже есть.*
  * **(б) Радиус = номер уровня, дуга рисуется только для реальных целей.** Тогда `{2,3}` —
    дуги на радиусах 2 и 3, а одна связь к уровню 3 — одна дуга далеко от точки, и «3»
    придётся считать по пустому месту. Информативнее, но читается хуже.
  * **(в) Комбинация:** слоты `1..max` рисуются бледной шкалой, реальные цели — сплошными.
    Самое информативное и самое дорогое в отрисовке.
* 🔴 **Связь `А1 ↔ А3` перепрыгивает уровень 2.** В каскадной раскладке (уровни идут
  вертикально вниз) прямая между рамками 1 и 3 пройдёт **прямо через окно уровня 2**,
  а глобальный слой лежит выше окон — то есть пунктир ляжет поверх чужого содержимого
  и нарушит §4.0. Нужно правило трассировки: если отрезок между прокси-портами пересекает
  другое окно, он **огибает его сбоку** по ближайшей стороне. Этого случая нет ни в плане v1,
  ни в §4.4 — он вылезает только на трёх и более уровнях.
* 🟡 **Транзитный уровень не помечается.** Связь `А1 ↔ А3` не имеет отношения к уровню 2,
  поэтому на рамке уровня 2 прокси **не появляется** — окно она только огибает.
  Соблазн показать «транзит» есть, но он врёт: связь не принадлежит этому уровню.
* 🟡 **Направление колец у прокси на противоположных рамках.** У прокси на нижней грани
  уровня 1 дуги смотрят вниз, у прокси на верхней грани уровня 3 — вверх. То есть одна связь
  даёт две зеркальные группы колец с разным числом (3 и 1). Это правильно — число кодирует
  цель, а не саму связь, — но в документации это надо проговорить, иначе будет читаться
  как ошибка.
* 🟡 **Слоты на рамке считаются от набора связей, а не от геометрии** (§4.4). После шага 1
  прокси к уровню 3 может сдвинуться в соседний слот, освобождая место новому. Переезд
  анимировать, чтобы это не выглядело как промах мимо цели.

### 4.8. Мастер-порт и свёрнутое окно

Мастер-порт живёт **на шапке окна**, а не на рамке. Причина прямая: шапка — единственная
часть окна, которая переживает сворачивание. Свёрнутое окно — это одна полоса-шапка,
и мастер-порт остаётся на месте вместе с ней.

Это и делает возможным сценарий, ради которого он затевался: узел-ассистент подключается
к мастер-портам нескольких уровней сразу, часть из которых свёрнута и не занимает места
на холсте.

**Правила сворачивания:**

* Содержимое окна не рендерится вовсе — ни узлы, ни слои, ни внутриуровневые связи.
* **Все прокси-порты схлопываются в мастер-порт**, а межуровневые связи окна сходятся
  в одну точку. На мастер-порте появляется бейдж со счётчиком схлопнутых связей.
  Разворачивание возвращает прокси по слотам.
* Связи к самому мастер-порту при сворачивании не меняются вообще — это его главное отличие
  от прокси.

**Подводные камни:**

* 🔴 **Мастер-порт — часть обвязки, а не содержимого** (§4.5): он не масштабируется
  внутренним зумом и не обрезается. Считается напрямую от `win.position`, минуя
  `innerOffset`/`innerZoom`.
* 🔴 **Мастер-порт нельзя удалить.** `DELETE_SELECTED` и `REMOVE_PORT` обязаны его
  пропускать: `if (port.isMaster) return;`. Иначе один `Delete` при выделенном порте
  оставит окно без адреса, а связи — висячими.
* 🔴 **Инвариант «ровно один на окно» надо восстанавливать, а не предполагать.**
  `ensureMasterPorts(state)` в `LOAD_STATE`, `UNDO`, `REDO` и миграции. Старые файлы окон
  не содержат вовсе, новые окна может создать любой экшен — единственная защита
  от «окна без мастер-порта» это нормализатор, а не дисциплина в каждом месте.
* 🔴 **Перенумерация уровней мастер-порта не касается** (§7.3): его `id` производен
  от стабильного `id` окна, а не от номера уровня. Поэтому связи ассистента переживают
  удаление уровня в середине цепочки. Ещё одна выгода от решения «номер — поле, а не ключ».
* 🟡 **Место на шапке.** Там уже живут название, глаз изоляции, цвет, сворачивание и закрытие.
  Мастер-порт должен получить фиксированный слот с краю, иначе при длинном названии
  он уедет под кнопки.
* 🟡 **Самоподключение.** Ассистент, лежащий внутри окна, не должен подключаться
  к мастер-порту этого же окна — это замыкание уровня на себя. Отбивать при создании связи.
* 🟡 **Кольца на мастер-порте не нужны.** Он и есть уровень, поэтому вместо колец
  целевого уровня на нём уместен бейдж с собственным номером уровня. Иначе он визуально
  сольётся с прокси-портами, которые кодируют кольцами совсем другое.
* 🟡 **Связка с ИИ-агентом.** В состоянии уже есть `ui.aiAgentSettings.contextMode`
  со значением `'global'`. Естественное развитие: контекст ассистента определяется тем,
  к мастер-портам каких уровней он подключён. Это не входит в объём работ по уровням,
  но модель данных должна такое позволять — то есть связь «узел → мастер-порт» обязана
  быть обычной связью, а не особым случаем.

## 7. Удаление уровней и авто-удаление пустых окон

### 7.1. Ручное удаление окна

* 🔴 Удаление окна = каскадное удаление всех уровней ниже. Требует подтверждения:
  сейчас `DELETE_SELECTED` по `Delete` молчаливый.
* 🔴 Всё удаление — **одним экшеном** (один снапшот истории), иначе Undo восстановит половину.
* 🔴 После удаления: пересчитать `levelIndex`, почистить висячие `ownerId`, удалить порты
  и связи удалённых узлов, реконсилить `activeLevelId`, `selectedIds`, `isolatedIds`.

### 7.2. Авто-удаление пустого окна (решение 3B)

Критерий: в окне не осталось **ни узлов, ни слоёв**.

* 🔴 **Точек, где окно может опустеть, больше одной:** `DELETE_SELECTED`, `REMOVE_NODE`,
  `REMOVE_LAYER`, `REPARENT_ENTITY` (последний узел перенесли в другое место), перетаскивание
  узла в соседнее окно, `MASS_UPDATE` со сменой `parentId`. Городить проверку в каждой —
  гарантированный пропуск. Нужен **один общий хелпер `pruneEmptyLevelWindows(state)`**,
  вызываемый в конце каждого изменяющего экшена.
* 🔴 **Удаление обязано попадать в тот же снапшот истории**, что и опустошившее его действие,
  иначе один Ctrl+Z вернёт узел, но не окно.
* 🔴 **Уровень 0 не удалять никогда.** Иначе пустой проект остаётся вообще без холста,
  и новому узлу некуда лечь.
* 🟡 Активный уровень мог быть удалён — `activeLevelId` откатывать на уровень 0.
* 🟡 Undo восстановит окно даром (решение 1A: окно внутри снапшота `layers`).

### 7.3. Перенумерация уровней (решение: удаляем и середину тоже)

Пустое окно удаляется в любой позиции цепочки, а все уровни ниже поднимаются
на одно поколение вместе со всем содержимым.

**Почему это оказалось дёшево — и почему только при выбранной модели данных.**
`levelIndex` — это **поле сущности, а не ключ словаря** (§9, фаза 1). Поэтому
перенумерация — один проход `levelIndex--` по окнам ниже удалённого. Идентификаторы окон
не меняются, значит не протухают ни `selectedIds`, ни `isolatedIds`, ни `activeLevelId`,
ни снапшоты в `past`/`future`. Сделай мы как в плане v1 (`levelWindows` с индексом в качестве
ключа) — перенумерация переписывала бы ключи словаря, и Undo после удаления уровня возвращал
бы состояние со ссылками на несуществующие окна.

**Содержимое трогать не нужно вообще.** Узлы остаются в своих окнах (`parentId` не меняется —
окно как сущность продолжает жить, у него меняется только номер). Поднятие потомков
«на поколение ближе» происходит само собой, потому что поднялось само окно.

**Что при этом важно не пропустить:**

* 🔴 **`ownerId` через опустевший уровень.** Пустой уровень посередине возможен только в одном
  случае: узлы из него не удалили, а **перенесли** в другое окно. Тогда потомки на уровне ниже
  ссылаются на владельцев, которые теперь живут выше. После перенумерации связь
  «владелец на уровень выше» восстанавливается сама — **но только если владелец действительно
  оказался ровно на один уровень выше**. Нужна проверка целостности после перенумерации:
  для каждого узла `levelIndex(окно узла) === levelIndex(окно владельца) + 1`. Нарушения —
  либо чинить переносом узла в правильное окно, либо гасить `ownerId` (узел становится
  самостоятельным). Это надо покрыть тестом отдельно: сценарий редкий, но данные бьёт молча.
* 🔴 **Каскад при удалении узла остаётся прежним.** Удалили узел-владельца — удаляются
  и все его потомки. Именно поэтому уровень посередине почти никогда не пустеет
  «сам по себе», а только после ручного переноса.
* 🟡 **Пространственное положение окон.** После удаления уровня в середине под ним остаётся
  дыра высотой в удалённое окно плюс зазор. Предлагаю сдвигать все окна ниже вверх ровно
  на `высота удалённого окна + 80px`, сохраняя их взаимное расположение — так каскад
  смыкается, а вручную расставленные окна не телепортируются к чужим местам.
* 🟡 **Уровень 0 не удаляется никогда**, даже пустой: иначе новому узлу некуда лечь.
* 🟡 **Всё в одном экшене** — и удаление, и перенумерация, и сдвиг окон. Один Ctrl+Z обязан
  возвращать всё целиком.

  таблица порядка, иначе шапка окна перекроет `ContextActionBar` (`z-40`, `top-16`).
* 🟡 **Клик в тело окна активирует уровень (инцидент 10)**, но не открывает панель свойств:
  это два разных события — `SET_LEVEL_FOCUS` (тело) и `SET_SELECTED` (шапка).

### Фаза 5. Контролы на узле: `+` и `📁 N`

* 🔴 **`calculateNodeSize` не знает о новых кнопках** (`reducer.js:95`). Ширина считается
  как `name.length * nameCharW + 75`, где `75` — запас под текущую шапку. Две кнопки справа
  съедят около 56px → заголовки начнут переноситься и прыгать при живом авторесайзе
  (AGENTS.md §9). Константу поднять, тесты авторесайза обновить.
* 🟡 В `Node.js` уже есть неиспользуемое состояние `isNodeHovered` (`Node.js:192`) —
  переиспользовать под кнопку `+`, не плодить новое.
* 🟡 `getChildrenStats` считает по `parentId` — бейдж `📁 N` обязан считать по **`ownerId`**.
  Легко пропустить: счётчик молча покажет 0.
* 🟡 Клик по бейджу не должен всплывать в `handleMouseDown` узла (сдвиг больше 3px запускает drag).
* 🟡 `FOCUS_CHILDREN_OF_NODE` не может пользоваться `getChildrenBBox` (`hierarchy.js:70`):
  та считает габариты в системе координат родителя, а дети теперь в другом окне и в другом
  масштабе. Нужен мировой габаритный прямоугольник через `getWorldTransform` по каждому ребёнку.

### Фаза 6. Связи и порты

* 🔴 **`Port.js` определяет межуровневость через `parentId`-контекст** (блок `isCrossLevel`
  и цикл `maxInternalDepth`, который ходит по `state.nodes[current.parentId]`). После
  расщепления полей обход упрётся в окно (окно лежит в `layers`, не в `nodes`) и молча
  вернёт 0 колец. Переписать на сравнение `levelIndex` владеющих окон.
* 🔴 **Разделение связей на два слоя** и перенос связи между слоями при смене окна (§4.3).
* 🔴 **Резолвер владельца порта** `getPortOwner` и перевод на него всех мест
  `state.nodes[port.nodeId]` (§4.4). Это самый широкий по охвату пункт фазы: пропущенное
  место не падает, а тихо возвращает `undefined`.
* 🔴 **Прокси-порты и мастер-порт** (§4.4): производные не хранить, мастер-порт хранить;
  раскладка по стабильным слотам вдоль грани; слой портов рамки — вне обрезаемого вьюпорта.
* 🔴 **Хуки строго наверх** (инциденты 7, 8) — должно быть уже сделано в фазе 0.5.
* 🔴 **Полукольца целевого уровня** (§4.5): рисуются и у порта узла, и у прокси-порта
  на рамке; кодировку доопределить, предел читаемости задать.
* 🔴 **Подключение связи к прокси-порту** (§4.6): общий сборщик целей `getDropTargets`,
  запреты, отключение «умного создания порта» над рамкой.
* 🟡 **Дуги не должны перехватывать мышь**: порт — цель для перетаскивания связи,
  SVG поверх него без `pointer-events: none` убьёт создание связей.
* 🟡 **Дуги у портов возле границы всё равно обрежутся рамкой** (§4.3). Смягчение —
  внутренний отступ окна; информация при этом не теряется, потому что тот же признак
  продублирован на рамке.
* 🟢 **Размер портов масштабируется вместе с содержимым** — решение принято, и это
  действительно почти даром: порт лежит внутри узла по DOM, поэтому масштаб окна применится
  к нему сам, ровно так же, как сейчас общий зум холста уменьшает порты вместе со всем.
  Два следствия, которые всё же надо доделать руками:
  **(а)** попадание по порту при перетаскивании связи считать **в экранных координатах**
  (§3.5) — иначе в ужатом окне порты станут почти некликабельными;
  **(б)** порог скрытия портов `zoom < 0.4` в `Node.js` заменить на `zoom * innerZoom < 0.4`.
* 🟡 **Толщина линий**: в масштабированном окне `strokeWidth: 2` превращается
  в `2 * innerZoom * zoom`. В отличие от портов, здесь масштабирование нежелательно —
  нужен `non-scaling-stroke` либо деление на масштаб, иначе одинаковые связи выглядят
  по-разному в разных окнах.
* 🟡 Пунктир `'2 6'` при малом суммарном масштабе исчезает — нужен порог видимости.
* 🟡 Сейчас пунктир не работает вообще из-за B3.

### Фаза 7. Панели, тулбар, изоляция, обозреватель

* 🔴 **`ContextActionBar` рендерится только при непустом `selectedIds`**
  (`ContextActionBar.js:194`). Режим «Свойства проекта» выделения не имеет — нужна отдельная
  ветка **до** этой проверки, иначе панель просто не появится.
* 🔴 **Шапка проекта конфликтует с `ContextActionBar` (`fixed top-16`)** и с `Toolbar`
  (`left-4`, по центру вертикали). Нужна согласованная сетка.
* 🔴 **Изоляция (инцидент 4).** `isolatedIds` фильтруется в `Canvas.js` при рендере.
  Нужно явное правило: если изолирован узел внутри окна — окно остаётся видимым (иначе узел
  повиснет в пустоте) или скрывается? Записать в `docs/UX.md` **до** реализации.
* 🟡 **Цвет плашки проекта (инцидент 6).** Классы вида `bg-emerald-500/20` статичны.
  Общее правило: **значение из состояния — это инлайн-стиль, а не класс.**
* 🟡 Поповер «перенести на слой» обязан фильтровать окна (§5).

7b. Панорамировать и зумировать содержимое окна → прокси-порты на рамке не ползают и не меняют размер.

7h. Добавить второй связи с другого уровня к тому же порту → на рамке появляется второй прокси со своим числом колец; подсказка при наведении на порт узла перечисляет обе цели.

8. Одинаковая связь в окне с зумом 1 и в окне с зумом 0.5 → **одинаковой видимой толщины**.
9. Потянуть связь из порта с дугами → дуги **не** перехватывают мышь.

13. Удалить последний узел из окна уровня 2 → окно исчезает; **один** Ctrl+Z возвращает и узел, и окно.

16. Открыть приложение со старым сохранением (v10) → проект цел, узлы в окне уровня 0.

## 12. Открытые вопросы

**1. Что создаётся при отпускании связи на пустом месте холста уровня?**
Для рамки решено: связь идёт к мастер-порту (§4.6). Для пустого места **внутри** окна
остаётся выбор — порт не может висеть без владельца:
* **(а)** создаётся новый узел с портом в точке отпускания — быстрое ветвление одним жестом;
* **(б)** ничего, как сейчас (связь отменяется).

Вариант «свободная точка подключения посреди холста» отпал сам: с появлением мастер-порта
у подключения к уровню есть единственный понятный адрес, и вторая сущность с той же
семантикой только запутает.

**2. Кодировка колец при связях сразу к нескольким уровням** — три варианта разобраны
в §4.7. По умолчанию беру (а): на порте узла кольца показывают самую дальнюю цель,
точный состав читается на рамке.

**3. Индикатор для связи с уровнем 0.** При кодировке «число контуров = номер уровня»
уровню 0 не достаётся ни одного контура, и такой порт неотличим от порта без межуровневых
связей. Нужен либо отдельный вид глифа для уровня 0, либо сдвиг шкалы на единицу.

Фаза 0 (§8) от всех трёх не зависит и может идти параллельно с их обсуждением.
