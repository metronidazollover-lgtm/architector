# PLAN V6 — Параллельные независимые виды проектов вместо общего слитого справочника

**Дата обновления:** 2026-08-28 (актуализировано с учетом реализации портов и связей слоев `REPORT_LAYER_PORTS_AND_LINKS`)  
**Повод переработки:** предыдущая концепция слияния всех проектов в единый глобальный словарь (`mergeActiveView`) отвергнута: слияние размножает коллизии id/номеров уровней, удорожает вычисления O(N) на кадр и ломает изоляцию историй. Направление — каждый проект держит свой независимый плоский вид (`projectFlatView`), пишет в свою историю через `FOR_PROJECT` / `writeProjectView`, а компоненты холста получают `projectId` через `ProjectContext`.  
**Статус:** В работе. Выполняется пошагово (1 шаг = отчёт и инструкция для ручной проверки).  
**Уточнение объёма по решению пользователя:** Межпроектный Drag & Drop (`TRANSFER_ACROSS_PROJECTS`) пока **отложен / не трогаем**. Фокус — на полноценной видимости, кликабельности, независимой истории и взаимодействии с неактивными проектами на общем холсте.  
**Предпосылка:** пользователю нужно, чтобы:  
(а) неактивные проекты были видны полностью, не приглушённым пустым огрызком;  
(б) были кликабельны и интерактивны наравне с активным (выделение, правка, внутрипроектный драг);  
(в) каждый проект сохранял изолированную историю Undo/Redo.

## 1. Факты из кода (сверено построчно 2026-08-28)

### 1.1 Корень проблемы — не хранилище, а единственная точка чтения

* `NodeView`/`PortView`/`Link` не принимают вид через пропсы — вызывают `useSelector(selectDerived)` (`Node.js:85-86`, `Port.js:88-93`, `Link.js:65-67`), который внутри всегда читает `architectorStore.getView()` (`Store.js:66-78`) — а это закэшированный `mergeActiveView(state)` (`reducer.js:3155-3168`), то есть **только активный проект**, без вариантов.
* `getStoreView()` — тот же `architectorStore.getView()` без подписки, используется в замыканиях обработчиков (`Node.js:98`, `Port.js:118,206`) — там же, тот же активный проект.
* Значит узел, порт или связь чужого (неактивного) проекта физически не могут отрисоваться или отреагировать на клик не потому, что где-то стоит блокирующий `if (isActive)`, а потому, что единственный источник данных для этих компонентов — глобальный синглтон, суженный до одного проекта на уровне движка стора.

### 1.2 `LevelWindow` и `CrossLevelLinkLayer` параметризованы явно, но вызывают дочерние компоненты

* `LevelWindow` принимает `windowData, nodes, layers, ports, links, selectedIds, isolatedIds, state, dispatch` через пропсы (`LevelWindow.js:5`).
* `CrossLevelLinkLayer` параметризован явно: `function CrossLevelLinkLayer({ projectState, dispatch, ... })` (`Canvas.js:8`), и это осознанное решение: «иначе у неактивных проектов на рамках висели бы прокси-порты без соединяющего их пунктира».
* Однако внутри `LevelWindow.js` (строки 904-1010) рендерятся `<Layer>`, `<Link linkId={link.id} />` и `<NodeComponent nodeId={node.id} />`. Так как `Link` и `Node` не получают словари через пропсы, а лезут в глобальный `useSelector`, они падают в контекст активного проекта.

### 1.3 `Layer.js` — расширившийся периметр зависимостей после добавления портов слоев

* `LevelWindow.js:904-917` передает в `<Layer>` пропсы `data, layer, nodes, layers, selectedIds, isolatedIds, dispatch, zoom`.
* Но внутри `Layer.js:5` компонент зовет глобальный `const { state, dispatch } = useStore()`.
* Из глобального `state` компонент берет:
  1. `state.nodes`, `state.layers` — для `getLocalPosition` (`Layer.js:38`, `Layer.js:77`), что ломает координаты вложенных слоев в чужих проектах;
  2. `state.ports`, `state.links` — для рендера портов слоя (`Layer.js:10-13`, `Layer.js:314-316`) и подсветки соединенной сети (`Layer.js:17-31`);
  3. `state.interactionMode` — для оверлея добавления портов на слой (`Layer.js:319-360`);
  4. `state.selectedIds`, `state.canvas.zoom`, `state.dragGesture`.
* При этом `Layer.js` диспатчит глобальные экшены `ADD_PORT`, `UPDATE_LAYER`, `MASS_UPDATE`, `FOCUS_CONNECTED_ELEMENTS`, `COMMIT_HISTORY` напрямую в активный проект вместо своего.
* **Вывод:** `Layer.js` требует перевода на проектный срез и проектный диспетчер наравне с `Node.js`, `Port.js` и `Link.js`.

### 1.4 Запись данных: адресная инфраструктура уже есть, просто не используется

* `delegateToActiveProject` (`reducer.js:3261-3279`) — ограничение на запись: экшен прогоняется через `mergeActiveView`, результат уходит только в `m.projects[m.activeProjectId]`.
* Рядом в том же файле уже существуют функции адресной работы с ЛЮБЫМ проектом:
  * `projectFlatView(m, pid)` / `writeProjectView(m, pid, flat)` (`reducer.js:3236-3253`) — прочитать/записать плоский вид конкретного проекта;
  * `FOR_PROJECT` (`reducer.js:3368-3379`) — экшен-обертка «прогнать внутренний экшен через `internal reducer` на виде конкретного `projectId`»;
  * `DELETE_SELECTED` (`reducer.js:3380-3427`) — уже реально пользуется этой парой функций для мульти-проектного удаления.
* UI пока не диспатчит `FOR_PROJECT` — весь интерфейс полагается на подразумеваемый активный проект.

### 1.5 `getDropTarget` не нужно переписывать — достаточно звать по разу на проект

* `HierarchyUtils.getDropTarget(draggedIds, pointerWorld, state, opts)` (`hierarchy.js:983-1087`) ищет цель в МИРОВЫХ координатах.
* Окна всех проектов уже находятся в общем мировом пространстве холста (`PROJECT_SLOT_GAP`).
* Функцию не нужно переписывать под объединенный словарь — достаточно вызывать ее в цикле по открытым проектам с плоским видом каждого проекта.

### 1.6 `resolveContainerSelection` — прецедент поиска владельца без общего индекса

`resolveContainerSelection` (`reducer.js:3288-3332`) находит проект окна перебором `Object.keys(m.projects)`. Это работает быстро и надежно без отдельного реверс-индекса.

### 1.7 Что уже глобально, без всякого плана

`selectedIds`, `dragGesture`, `pendingConnection`, `canvas`, `ui`, `clipboard` — не входят в `PROJECT_FIELDS` (`reducer.js:3102-3108`), то есть уже сегодня один экземпляр на все проекты. Мультивыделение контейнеров нескольких проектов через префиксы `project:pid`/`window:wid` уже поддерживается.

### 1.8 Стабильность ссылки на вид (`useSyncExternalStore`) и гранулярный кэш

`StoreEngine.createStore` (`engine.js:28-56`) пересчитывает `view` ровно один раз на изменение состояния. `projectFlatView` создает новый объект при каждом вызове. 
**Важнейший нюанс кэширования:** кэш среза проекта `getProjectFlatView(projectId)` должен инвалидироваться строго по ссылке на сам срез проекта `state.projects[projectId]`, а **не** по глобальному корню `rootState`. В глобальном `rootState` живут поля вроде `pointerWorld` или `dragGesture`, меняющиеся до 60 раз в секунду при любом движении мыши. Кэширование по `state.projects[projectId]` гарантирует, что пока внутри проекта Б ничего не изменилось, его плоский вид возвращает стабильную ссылку, и React не запускает холостые перерисовки узлов чужих проектов (см. §3.1).

### 1.9 Порты и связи: сохранение границы проекта (для Узлов и Слоев)

Весь сценарий протягивания связи (`Port.js:195-360`) теперь поддерживает как узлы, так и слои (`nodes[id] || layers[id]`). Поиск ближайшего порта и цели дропа должен быть строго изолирован пределами текущего проекта (см. §3.4, §3.5).

## 2. Принятое направление

Каждый проект остается при своем независимом, узком виде — как и сегодня для активного — и пишет в свою собственную историю Undo сам через `FOR_PROJECT`/`projectFlatView`/`writeProjectView`. Ничего не сливается в один общий словарь. 

На холсте одновременно существуют виды для каждого открытого проекта из `projectOrder`, и каждый компонент окна знает свой `projectId` через `ProjectContext`.

Преимущества:
* `LevelWindow` и `CrossLevelLinkLayer` не ломаются.
* Запись использует уже готовые `FOR_PROJECT`/`projectFlatView`/`writeProjectView`.
* Нет коллизий уровней (L0 в проекте А и L0 в проекте Б изолированы).
* Межпроектные связи не могут возникнуть случайно.
* Производительность O(1) относительно числа сторонних проектов: селекторы узлов/портов/слоев/связей вычисляются только по словарям своего проекта.

## 3. Целевая модель

### 3.1 Гранулярный кэш вида по проекту `getProjectFlatView(projectId)`

В `Store.js` (на базе `engine.js`):
* Хранит `Map<projectId, { lastProjectState, flatView }>`.
* При запросе `getProjectFlatView(projectId)` проверяет `state.projects[projectId] === cache.lastProjectState`.
* Если сам объект проекта не мутировал в Redux, возвращает стабильную ссылку `flatView` без пересчета (движение мыши, зум и экшены в чужих проектах не сбрасывают этот кэш!).
* Если `state.projects[projectId]` изменился — лениво пересчитывает `projectFlatView(state, projectId)`.
* Экспортировать `projectFlatView` из `reducer.js` в `ArchitectorStore` (`reducer.js:3572`).

### 3.2 `ProjectContext`

В `Store.js`:
```js
const ProjectContext = React.createContext(null);
```
Значение: `projectId` (строка) или `null` (по умолчанию — активный проект).

### 3.3 `useProjectSelector` / `useProjectDispatch`

* `useProjectSelector(selector, isEqual)`: читает `projectId = useContext(ProjectContext)` и берет `projectId ? getProjectFlatView(projectId) : architectorStore.getView()`.
* `useProjectDispatch()`: возвращает функцию `dispatch`, которая при наличии `projectId && projectId !== activeProjectId` заворачивает экшен в `{ type: 'FOR_PROJECT', payload: { projectId, action } }`. Для активного проекта или `projectId === null` диспатчит напрямую.

### 3.4 Перевод компонентов: `Node.js`, `Port.js`, `Layer.js`, `Link.js`

1. **`Node.js`**: `useSelector` → `useProjectSelector`; `useDispatch` → `useProjectDispatch`; `getStoreView()` → `getProjectFlatView(projectId)`.
2. **`Port.js`**: `useSelector` → `useProjectSelector`; `useDispatch` → `useProjectDispatch`; замыкания поиска портов/узлов/слоев используют `getProjectFlatView(projectId)`.
3. **`Layer.js`**: замена `useStore()` на `useProjectSelector` для чтения `nodes`, `layers`, `ports`, `links`, `zoom`, `interactionMode`, `selectedIds`, `dragGesture`. Замена вызовов `dispatch` на `useProjectDispatch()`.
4. **`Link.js`**: `useSelector` → `useProjectSelector`; `useDispatch` → `useProjectDispatch`. В рендере обязательна защитная проверка: `if (!source || !target) return null;`.
5. **`LevelWindow.js`**, **`CrossLevelLinkLayer`**: оборачиваются в `<ProjectContext.Provider value={project.id}>` (см. §3.6).

### 3.5 Защита от межпроектных связей (Узлы и Слои) с прицелом на PLAN V7

*Так как межпроектные взаимодействия и перенос элементов запланированы отдельно в PLAN V7, в V6 действует строгий изолирующий барьер:*
* **Защита:** В `Port.js` и в экшене `ADD_LINK` редьюсера жестко блокировать создание связи, если порты принадлежат разным `projectId`, а в `Link.js` добавить защитное условие `if (!source || !target) return null;`.
* При протягивании связи (`Port.js: handleMouseUp`) поиск целей (ближайший порт, прокси-порт, дроп на узел, дроп на грань слоя) ведется строго по плоскому виду проекта исходного порта (`getProjectFlatView(sourceProjectId)`).

### 3.6 Интерактивность неактивных проектов на холсте и Drag Overlay

Существующий блок `Canvas.js:644-726` (блок неактивных проектов):
* Снимается `pointer-events-none` с интерактивных элементов окон неактивных проектов.
* Сохраняется визуальное приглушение неактивных проектов (opacity / border styling).
* Каждый рендеримый `LevelWindow` (или контейнер проекта) оборачивается в `<ProjectContext.Provider value={proj.id}>`.
* Активный проект также оборачивается в `<ProjectContext.Provider value={activeProjectId}>` для единообразия.
* **Защита Drag Overlay:** в `Canvas.js` глобальный оверлей перетаскиваемых элементов (`dragGesture`) обязан получать `dragGesture.projectId` и оборачиваться в `<ProjectContext.Provider value={dragGesture.projectId}>`, чтобы перетаскиваемый узел не терял свой проект и не исчезал.
* При клике на элемент неактивного проекта Б происходит мягкая синхронизация активного проекта для внешних панелей (`ContextActionBar`, `Library`), чтобы панель свойств отображала реальные параметры выбранного узла/слоя.
