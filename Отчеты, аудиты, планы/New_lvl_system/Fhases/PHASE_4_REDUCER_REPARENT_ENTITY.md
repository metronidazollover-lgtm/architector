## 📋 Подробный состав задач Фазы 4

### 4.1. Расширение экшена `REPARENT_ENTITY`
Новая спецификация экшена (заменяет текущий узкий контракт `{ id, newParentId }`):
```js
{
  type: 'REPARENT_ENTITY',
  payload: {
    ids: ['node-1', 'layer-2'],        // Массив перемещаемых сущностей
    targetParentId: 'layer-x' | 'node-y' | 'root', // Целевой контейнер
    targetLevelIndex?: number,         // Если сброс на пустое окно уровня
    mode?: 'deep' | 'shallow',         // По умолчанию 'deep'
    position?: { x, y }                // Опциональные новые координаты
  }
}
```
- **Обратная совместимость:** старый одиночный вызов `{ id, newParentId }` нормализуется в начале case в `{ ids: [id], targetParentId: newParentId }` — на время переходного периода (пока оба теста на старый контракт не переписаны на новый).
- **Переносится без изменений** из текущей реализации: проверка цикла через `isDescendantOf`, запрет вложения узла в слой чужого уровня (сравнение `getEntityLevel` слоя и сущности).

### 4.2. Реализация режима Deep (по умолчанию)
- Проверка защиты от циклов `!isDescendantOf(targetParentId, id)`.
- Назначение `newNodes[id].parentId = targetParentId`.
- Дочерние элементы (`children`) остаются без изменений и автоматически перемещаются вместе с родителем.

### 4.3. Реализация режима Shallow (вырывание узла)
- Для каждого вырываемого узла `nodeId`:
  1. Находим его текущего родителя `oldParentId = node.parentId`.
  2. Находим всех его прямых детей `directChildren = Object.values(nodes).filter(n => n.parentId === nodeId)`.
  3. Каждому прямому ребенку назначаем `parentId = oldParentId` (усыновление дедушкой).
  4. Запускаем `GeometryUtils.findFreePosition` для предотвращения наложения всплывающих детей.
  5. Перемещаемому узлу назначаем `parentId = targetParentId`.

### 4.4. Атомарность истории (Atomic Undo/Redo)
- Вся операция `REPARENT_ENTITY` (перенос родителя + усыновление детей + пересчет связей) сохраняется в `historyState` как **один неделимый шаг**.
- При `Ctrl+Z` вся конфигурация мгновенно возвращается на исходные позиции.

### 4.5. Упрощение операций удаления (`REMOVE_NODE`, `REMOVE_LAYER`, `CLEAR_LEVEL_WINDOW`)
- `REMOVE_NODE`: при удалении узла его дети либо каскадно удаляются (если удаляется вся ветка), либо всплывают к дедушке без gap-костылей.
- `CLEAR_LEVEL_WINDOW`: удаляет только узлы, чей уровень равен выбранному, без разрушения структуры других уровней.

### 4.6. Покрытие юнит-тестами (`app/tests/reducer.test.js`)
- Тест 1: Deep перенос 3-уровневой ветки в новый слой.
- Тест 2: Shallow вырывание среднего узла с проверкой усыновления детей дедушкой.
- Тест 3: Откат (Undo) и повтор (Redo) для Deep и Shallow операций.
- Тест 4: Защита от циклических вложений (попытка бросить родителя в ребенка $\rightarrow$ no-op).
- Тест 5: Обновить два существующих теста на старый контракт `{ id, newParentId }` (строки 1295, 1299) под новую форму payload — либо переписать на `{ ids, targetParentId }`, либо явно проверить, что старая форма всё ещё нормализуется корректно.
