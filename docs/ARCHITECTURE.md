## Слой доставки состояния (2026-08-24)

Состояние приложения живёт **вне React** — в движке `app/store/engine.js`, который не знает про React и покрыт юнит-тестами в Node (`app/tests/engine.test.js`).

```
reducer.js (чистая логика)
   ↓
engine.js  createStore(multiReducer, initial, { project: mergeActiveView })
   ↓  getState / getView / dispatch / subscribe
Store.js   useStore() · useSelector() · useDispatch() · getStoreView()
   ↓
components/*
```

**Почему не useReducer + контекст.** Значение контекста `{ state, dispatch }` пересоздавалось на каждый `dispatch`, поэтому любое действие перерисовывало все компоненты, читающие стор. При перетаскивании узла это 60–120 полных перерисовок сцены в секунду; `React.memo` не помогал, потому что контекст обходит мемоизацию стороной.

**Свойства движка.**

* `getView()` возвращает плоский вид активного проекта по **стабильной ссылке**: проекция считается один раз на изменение состояния. Нестабильная ссылка зациклила бы `useSyncExternalStore`.
* Если редьюсер вернул то же состояние по ссылке, подписчики **не** уведомляются: экшены-пустышки (правка несуществующего id, жест без смещения) перестают стоить кадр.
* `dispatch` стабилен на всё время жизни приложения и больше не инвалидирует `useCallback` / `useEffect`.

**Правило подписки (важно для новых компонентов).** Селектор получает полный вид и считает производные значения через `HierarchyUtils`; решение о перерисовке принимается сравнением РЕЗУЛЬТАТА. Подписка на «свою запись» (`state.nodes[myId]`) недопустима: она теряет «рябь» — перенос предка, смену владельца, «глаз» на верхнем уровне, подсветку связанной сети. Регрессионные тесты ряби — `app/tests/reactivity.test.js`.

**Обработчики событий** читают состояние через `getStoreView()` в момент события, а не замыкаются на состояние времени рендера: компонент теперь может не перерисовываться десятки кадров подряд, и такое замыкание успело бы устареть.

### Проектно-адресный слой поверх Store.js (`ProjectContext`, 2026-08-28)

`getView()`/`useStore()`/`useSelector()` из предыдущего раздела всегда возвращают плоский вид ТОЛЬКО активного проекта (`mergeActiveView`) — этого контракта до PLAN V6 хватало, потому что окна неактивных проектов не принимали ввод. PLAN V6 сделал их полностью интерактивными (клик, выделение, драг, инлайн-правка прямо в неактивном проекте), а значит компонентам холста понадобился доступ к СВОЕМУ проекту, а не всегда к активному. Поверх того же движка (`Store.js`) добавлен второй, проектно-адресный путь получения данных:

```
reducer.js (чистая логика, без изменений)
   ↓
engine.js  createStore(multiReducer, initial, { project: mergeActiveView })
   ↓  getState / getView / dispatch / subscribe
Store.js   ├─ useStore() · useSelector() · useDispatch() · getStoreView()      — плоский вид АКТИВНОГО проекта (как раньше)
           └─ ProjectContext · getProjectFlatView(pid) · useProjectSelector() · useProjectDispatch()  — плоский вид ЛЮБОГО проекта
   ↓
components/*
```

* **`ProjectContext`** — React-контекст с `projectId` конкретного окна на холсте (`null` = активный проект). `Canvas.js` оборачивает в `<ProjectContext.Provider value={projectId}>` окна активного проекта, окна каждого неактивного проекта и Drag-оверлей перетаскиваемого элемента (по `dragGesture.projectId`, чтобы переносимый узел не терял свой проект при перерисовке).
* **`getProjectFlatView(projectId)`** — гранулярный кэш плоского вида проекта: `Map<projectId, { lastProjectState, flatView }>` в `Store.js`. Инвалидируется строго по ссылке на срез `state.projects[projectId]`, а НЕ по общему корню состояния — иначе движение мыши (`pointerWorld`, до 60 раз/сек) или экшен в чужом проекте сбрасывали бы кэш всех проектов разом и убивали FPS.
* **`useProjectSelector(selector)` / `useProjectDispatch()`** — читают `projectId` из `ProjectContext`; чтение идёт через `getProjectFlatView(projectId)`, а `dispatch` для проекта, отличного от активного, автоматически заворачивает экшен в `{ type: 'FOR_PROJECT', payload: { projectId, action } }` (адресная доставка в конкретный проект без смены активного, реализована в `multiReducer`). Для `projectId === null` или активного проекта — поведение как у обычного `useSelector`/`useDispatch`.
* На этот путь переведены компоненты холста: `Node.js`, `Port.js`, `Frame.js`, `Lane.js`, `LaneWindow.js`, `Link.js` (v14 — заменили `Layer.js`/`LevelWindow.js`, физически удалены в Фазе 6). Панели (`Toolbar.js`, `Library.js`, `ContextActionBar.js`) остались на старом пути и осознанно работают только с активным проектом.
* **`useProjectStore()`** (2026-08-29) — аналог `useStore()` (весь плоский вид + `dispatch`, без селектора), но привязанный к `ProjectContext` через `getProjectFlatView`/`useProjectDispatch`. Введён для `AIAgentNodeContent.js`: узел-ассистент рендерится внутри `NodeView` конкретного проекта, поэтому обязан читать/писать СВОЙ проект. До этой правки узел использовал `useStore()` и в неактивном проекте молча читал и менял данные активного проекта — баг того же семейства, что чинили для окон уровней (`REPORT_LEVEL_WINDOW_PROJECT_ROUTING`).
* **Кросс-проектные связи (v14, Фаза 5).** Поиск цели связи в `Port.js` сначала ищет в своём проекте, затем — сканирует остальные через `getProjectFlatView(pid)` + `HierarchyUtils.getPortWorldPositionV14`; найденный порт в чужом проекте диспатчит `ADD_CROSS_PROJECT_LINK` (обрабатывается в `multiReducer` напрямую, живёт в `state.crossProjectLinks`, глобальное поле вне истории Undo). Рендер — `Canvas.js`'s `CrossProjectLinkLayer`, одна прямая линия в мировых координатах (тем же приёмом, что `CrossWindowLinkLayer` для связей между дорожками одного проекта) — отдельной прокси-геометрии на грани окна в v14 не нужно. См. AGENTS.md, «Кросс-проектные связи». **Перенос узла/ветки между проектами (v14, Фаза 5)** — `applyCrossProjectReparent` в `multiReducer` (`isDescendantOfV14`/`canReparentToV14`, только узлы); живого UI-пути к нему пока нет — `Node.js`/`HierarchyUtils.resolveDropTarget` сканируют только свой проект, см. AGENTS.md, «Кросс-проектный перенос сущностей» / «Кросс-проектный Drag&Drop».

### Индексы и кэши (поколение = ссылка на словарь)

Все кэши в `hierarchy.js` ключуются по ссылке на словарь сущностей через `WeakMap`: редьюсер иммутабелен, поэтому смена ссылки означает смену поколения и автоматически инвалидирует кэш.

| Функция | Что даёт |
|---|---|
| `getPortsByNodeId` / `getLinksByPortId` | Порты узла и связи порта за O(1) вместо перебора словаря |
| `getChildrenByParent` | Прямые дети узла по `parentId` (v14 — единственная структура родства, слоёв в цепочке нет) |
| `getFramesByMember` / `framesOf` | Рамки, в которых состоит узел, по индексу членства |
| `getLinkOrderIndex` | Порядковый номер связи (разводит параллельные линии) без `indexOf` |
| `getLinksCrossingWindows` / `getProxyIndexForWindowV14` | Связи, пересекающие границу окна (дорожки концов открыты в разных окнах), по id окна/связи |
| `getDepth` (внутренний кэш) | Глубина узла без обхода цепочки `parentId` |
| `getLevel` (внутренний кэш, только миграторы) | v13-уровень сущности по цепочке `ownerId`/`parentId` — вызывается напрямую `migrateProjectEntitiesToV13`/`normalizeLevelWindows`, живой (не мигрирующий) код к нему не обращается |

**Ловушка, которую здесь легко повторить:** литерал вида `nodes || {}` создаёт НОВЫЙ объект при каждом вызове. Если такой объект попадает в ключ кэша, кэш промахивается всегда. Для этого заведена стабильная пустышка `EMPTY_DICT`.

**Порты и связи рамок (v14).** `HierarchyUtils.getPortWorldPositionV14` и компоненты `Port.js`/`Link.js`/`Frame.js`/`Lane.js`/`LaneWindow.js`/`Canvas.js` разрешают хост-сущность порта полиморфно: `state.nodes[id] || state.frames[id]`. Рамка — полноправный участник графа связей наравне с узлом (Рамка ↔ Рамка, Рамка ↔ Узел); порты рамки живут на куске в её `homeLaneId` (см. AGENTS.md, «Порты и связи рамок»).

### Отсечение по вьюпорту (culling) — известный пробел v14

v13 (`LevelWindow`) не создавал сущности, чьи прямоугольники не пересекают видимую область, с запасом в один экран по каждой стороне — стоимость кадра не зависела от размера сцены (см. `docs/BENCHMARKS.md`). **v14 (`Lane.js`/`LaneWindow.js`) этот механизм пока не переносило** — количество смонтированных узлов растёт линейно со сценой; на большом проекте (тысячи узлов) это заметно проседает по FPS. Задокументировано в `docs/BENCHMARKS.md`, «Фаза 5 (v14)» — отдельная задача, не решённая в рамках перехода на Дорожки/Окна/Рамки.

### Изоляция контейнеров — единственная ось видимости в v14

| Поле состояния | Единая точка истины | Что скрывает |
|---|---|---|
| `containerIsolation` | `isWindowVisible` / `isProjectVisible` | Окна и проекты целиком на общем холсте |

v13 (Фаза 6, удалено) имела вторую, независимую ось — «глаз» веток (`levelHideNeighbors`/`levelFocusParentId`, `HierarchyUtils.isEntityVisible`), скрывавшую отдельные сущности внутри уровня. В v14 такого понятия нет: видимость узла определяется исключительно тем, открыта ли дорожка его родителя хоть в одном окне (`HierarchyUtils.windowsOfLane`) — см. §2.3 `docs/LANES_MODEL.md`. Изоляция контейнеров в историю Undo не входит и автоматически снимается при удалении изолированного контейнера.

### Дорожки-зеркала

`window.lanes` — массив `ownerId`, не эксклюзивное владение: одна и та же дорожка (например, `'root'` или id узла) может быть открыта сразу в НЕСКОЛЬКИХ окнах одновременно — «зеркала». Это не требует отдельного кода: `Lane.js`/`Frame.js`/`Link.js` вычисляют своё содержимое из `state` заново при каждом рендере (та же дисциплина «подписка на вычисленный результат», что и везде в этом документе), поэтому перенос узла внутри дорожки, открытой в двух окнах, отражается в ОБОИХ мгновенно и структурно — см. тест «v14 дорожки-зеркала» в `reducer.test.js`. Единственное окно-источник для Drag&Drop-оверлея — `dragGesture.windowId`; остальные зеркала просто перерисовываются из данных после `mouseup`.

### Пакетная история

`BEGIN_HISTORY_BATCH` → серия экшенов → `COMMIT_HISTORY` записывает **один** шаг Undo на всю серию; `saveHistory` внутри пакета не пишет ничего. Механизм работает для любого экшена (не требует поддержки `skipHistory` в каждом) и используется применением команд ИИ и массовым закрытием окон (`DELETE_SELECTED` на нескольких выделенных `window:`). Аварийный выход — `CANCEL_HISTORY_BATCH`: прерванная операция не должна оставить историю выключенной.
