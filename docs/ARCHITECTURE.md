## Слой доставки состояния (2026-08-24)

Состояние приложения живёт **вне React** — в движке `app/store/engine.js`, который не знает про React и покрыт юнит-тестами в Node (`app/tests/engine.test.js`).

```
reducer.js (чистая логика)
   ↓
engine.js  createStore(multiReducer, initial, { project: mergeActiveView })
   ↓  getState / getView / dispatch / subscribe
Store.js   useStore() · useSelector() · useDispatch() · getStoreView()
   ↓
components/*
```

**Почему не useReducer + контекст.** Значение контекста `{ state, dispatch }` пересоздавалось на каждый `dispatch`, поэтому любое действие перерисовывало все компоненты, читающие стор. При перетаскивании узла это 60–120 полных перерисовок сцены в секунду; `React.memo` не помогал, потому что контекст обходит мемоизацию стороной.

**Свойства движка.**

* `getView()` возвращает плоский вид активного проекта по **стабильной ссылке**: проекция считается один раз на изменение состояния. Нестабильная ссылка зациклила бы `useSyncExternalStore`.
* Если редьюсер вернул то же состояние по ссылке, подписчики **не** уведомляются: экшены-пустышки (правка несуществующего id, жест без смещения) перестают стоить кадр.
* `dispatch` стабилен на всё время жизни приложения и больше не инвалидирует `useCallback` / `useEffect`.

**Правило подписки (важно для новых компонентов).** Селектор получает полный вид и считает производные значения через `HierarchyUtils`; решение о перерисовке принимается сравнением РЕЗУЛЬТАТА. Подписка на «свою запись» (`state.nodes[myId]`) недопустима: она теряет «рябь» — перенос предка, смену владельца, «глаз» на верхнем уровне, подсветку связанной сети. Регрессионные тесты ряби — `app/tests/reactivity.test.js`.

**Обработчики событий** читают состояние через `getStoreView()` в момент события, а не замыкаются на состояние времени рендера: компонент теперь может не перерисовываться десятки кадров подряд, и такое замыкание успело бы устареть.

### Проектно-адресный слой поверх Store.js (`ProjectContext`, 2026-08-28)

`getView()`/`useStore()`/`useSelector()` из предыдущего раздела всегда возвращают плоский вид ТОЛЬКО активного проекта (`mergeActiveView`) — этого контракта до PLAN V6 хватало, потому что окна неактивных проектов не принимали ввод. PLAN V6 сделал их полностью интерактивными (клик, выделение, драг, инлайн-правка прямо в неактивном проекте), а значит компонентам холста понадобился доступ к СВОЕМУ проекту, а не всегда к активному. Поверх того же движка (`Store.js`) добавлен второй, проектно-адресный путь получения данных:

```
reducer.js (чистая логика, без изменений)
   ↓
engine.js  createStore(multiReducer, initial, { project: mergeActiveView })
   ↓  getState / getView / dispatch / subscribe
Store.js   ├─ useStore() · useSelector() · useDispatch() · getStoreView()      — плоский вид АКТИВНОГО проекта (как раньше)
           └─ ProjectContext · getProjectFlatView(pid) · useProjectSelector() · useProjectDispatch()  — плоский вид ЛЮБОГО проекта
   ↓
components/*
```

* **`ProjectContext`** — React-контекст с `projectId` конкретного окна на холсте (`null` = активный проект). `Canvas.js` оборачивает в `<ProjectContext.Provider value={projectId}>` окна активного проекта, окна каждого неактивного проекта и Drag-оверлей перетаскиваемого элемента (по `dragGesture.projectId`, чтобы переносимый узел не терял свой проект при перерисовке).
* **`getProjectFlatView(projectId)`** — гранулярный кэш плоского вида проекта: `Map<projectId, { lastProjectState, flatView }>` в `Store.js`. Инвалидируется строго по ссылке на срез `state.projects[projectId]`, а НЕ по общему корню состояния — иначе движение мыши (`pointerWorld`, до 60 раз/сек) или экшен в чужом проекте сбрасывали бы кэш всех проектов разом и убивали FPS.
* **`useProjectSelector(selector)` / `useProjectDispatch()`** — читают `projectId` из `ProjectContext`; чтение идёт через `getProjectFlatView(projectId)`, а `dispatch` для проекта, отличного от активного, автоматически заворачивает экшен в `{ type: 'FOR_PROJECT', payload: { projectId, action } }` (адресная доставка в конкретный проект без смены активного, реализована в `multiReducer`). Для `projectId === null` или активного проекта — поведение как у обычного `useSelector`/`useDispatch`.
* На этот путь переведены компоненты холста: `Node.js`, `Port.js`, `Layer.js`, `Link.js`. Панели (`Toolbar.js`, `Library.js`, `ContextActionBar.js`) остались на старом пути и осознанно работают только с активным проектом.
* **`useProjectStore()`** (2026-08-29) — аналог `useStore()` (весь плоский вид + `dispatch`, без селектора), но привязанный к `ProjectContext` через `getProjectFlatView`/`useProjectDispatch`. Введён для `AIAgentNodeContent.js`: узел-ассистент рендерится внутри `NodeView` конкретного проекта, поэтому обязан читать/писать СВОЙ проект. До этой правки узел использовал `useStore()` и в неактивном проекте молча читал и менял данные активного проекта — баг того же семейства, что чинили для окон уровней (`REPORT_LEVEL_WINDOW_PROJECT_ROUTING`).
* **Кросс-проектные связи реализованы (Фаза 6.1, `PLAN_V12_CLEAN_HIERARCHY_AND_INTERACTIONS.md`).** Поиск цели связи в `Port.js` сначала ищет в своём проекте, затем — сканирует остальные через `getProjectFlatView(pid)`; найденный порт в чужом проекте диспатчит `ADD_CROSS_PROJECT_LINK` (обрабатывается в `multiReducer` напрямую, живёт в `state.crossProjectLinks`, глобальное поле вне истории Undo). Прокси-геометрия связей расширена на границу проекта — см. AGENTS.md, «Кросс-проектные связи». **Перенос узла/ветки между проектами реализован (Фаза 6.3)** — тем же живым Drag&Drop-жестом, что и внутри проекта: `getDropTarget`/`computeDropPositions`/`canReparentTo` получили опциональный `sourceState`/`entityDicts`, новая `getDropTargetAcrossProjects` сканирует все открытые проекты, `REPARENT_ENTITY` с `targetProjectId` перехватывается в `multiReducer` (`applyCrossProjectReparent`) — см. AGENTS.md, «Кросс-проектный перенос сущностей».

### Индексы и кэши (поколение = ссылка на словарь)

Все кэши в `hierarchy.js` ключуются по ссылке на словарь сущностей через `WeakMap`: редьюсер иммутабелен, поэтому смена ссылки означает смену поколения и автоматически инвалидирует кэш.

| Функция | Что даёт |
|---|---|
| `getPortsByNodeId` / `getLinksByPortId` | Порты узла и связи порта за O(1) вместо перебора словаря |
| `getNodesByParentId` / `getLayersByParentId` | Дети координатного контейнера |
| `getLinkOrderIndex` | Порядковый номер связи (разводит параллельные линии) без `indexOf` |
| `getCrossLinksByLevel` | Межуровневые связи, разложенные по уровням, одним проходом |
| `getEntitiesByLevel` | Сущности по уровням — общее для всех окон разложение |
| `getProxyIndexForWindow` | Прокси-порты окна по id связи |
| `getLevel` (внутренний кэш) | Уровень сущности без обхода цепочки владения |

**Ловушка, которую здесь легко повторить:** литерал вида `layers || {}` создаёт НОВЫЙ объект при каждом вызове. Если такой объект попадает в ключ кэша, кэш промахивается всегда. Для этого заведена стабильная пустышка `EMPTY_DICT`.

**Порты и связи слоёв (2026-08-28).** `getPortWorldPosition`, `getCrossLinksByLevel` и производные от них компоненты (`Port.js`, `Link.js`, `LevelWindow.js`, `Canvas.js`) разрешают хост-сущность порта полиморфно: `state.nodes[id] || state.layers[id]`. Слой — полноправный участник графа связей наравне с узлом (Слой ↔ Слой, Слой ↔ Узел), формат хранения не менялся (`formatVersion: 11`).

### Отсечение по вьюпорту (culling)

`LevelWindow` не создаёт сущности, чьи прямоугольники не пересекают видимую область (`getVisibleLocalRect` + `isRectVisible`), с запасом в один экран по каждой стороне. Безусловные исключения — участники активного жеста и выделенное: их размонтирование оборвало бы перетаскивание и подсветку. Окно целиком за экраном не рендерит содержимое вовсе.

Критерий один — **видимость на экране**. Активность проекта, активность уровня и выделение на качество отрисовки не влияют: неактивные проекты рисуются в том же качестве, что активный.

### Две оси видимости

| Ось | Поле состояния | Единая точка истины | Что скрывает |
|---|---|---|---|
| «Глаз» веток | `levelHideNeighbors` + `levelFocusParentId` | `HierarchyUtils.isEntityVisible` | Сущности внутри уровня |
| Изоляция контейнеров | `containerIsolation` | `isWindowVisible` / `isProjectVisible` | Окна уровней и проекты целиком на общем холсте |

Смешивать их в одном поле нельзя: они отвечают на разные вопросы и включаются разными кнопками. Изоляция контейнеров в историю Undo не входит и автоматически снимается при удалении изолированного контейнера.

### Пакетная история

`BEGIN_HISTORY_BATCH` → серия экшенов → `COMMIT_HISTORY` записывает **один** шаг Undo на всю серию; `saveHistory` внутри пакета не пишет ничего. Механизм работает для любого экшена (не требует поддержки `skipHistory` в каждом) и используется применением команд ИИ и массовым удалением уровней. Аварийный выход — `CANCEL_HISTORY_BATCH`: прерванная операция не должна оставить историю выключенной.
