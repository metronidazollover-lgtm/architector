## v11 → v12: мультипроектная обёртка

**Что изменилось.** Состояние перестало быть плоским. Прежний корень (сущности, окна уровней, камеры, история) целиком переехал внутрь одного проекта, а над ним появился слой мультипроектности:

```
{
  formatVersion: 12,
  projects: { <projectId>: { id, origin, ...все поля проекта } },
  projectOrder: [<projectId>, ...],
  activeProjectId: <projectId>,
  projectCounter: <number>,
  canvas, ui, selectedIds, ...        // глобальные поля, общие для всех проектов
}
```

**Поля проекта** (`PROJECT_FIELDS`): `projectName`, `projectColor`, `projectFontFamily`, `projectContent`, `levelWindows`, `levelViews`, `activeLevelIndex`, `levelFocusParentId`, `levelHideNeighbors`, `layers`, `nodes`, `ports`, `links`, `past`, `future`, `historyLogs`.

Ключевое следствие: **история Undo у каждого проекта своя** — отмена в одном проекте не затрагивает соседний.

**Как выполняется миграция.** `wrapFlatToMulti(flat)` заворачивает любое плоское состояние (v9/v10/v11 после соответствующих миграций) в один проект. Обратной операции нет: `mergeActiveView(m)` строит плоский ВИД активного проекта для компонентов и внутреннего редьюсера, поэтому весь прежний код продолжает читать `state.nodes` без изменений.

**Ключ хранилища:** `architector_state_v12`. Легаси-ключи не удаляются.

**Уникальность id окон.** Окна разных проектов не должны иметь общих id: они служат React-ключами и адресуют окно в выделении. Первый (мигрированный) проект сохраняет зарезервированный `lvlwin-root`, новые проекты получают сгенерированные id.

### Что НЕ переживает перезагрузку страницы (с 2026-08-24)

Массивы `past` / `future` очищаются перед записью в `localStorage`. История Undo полностью работает в пределах вкладки, но после перезагрузки страницы начинается с чистого листа. Это сознательный размен: 20 снимков сущностей на проект гарантированно переполняли квоту браузера (~5 МБ) на сколько-нибудь крупном проекте, после чего приложение навсегда оставалось в аварийном режиме сохранения.

Также не персистится транзиентное поле `historyBatch` (маркер открытого пакета истории).

### Поля, добавленные после v12

Аддитивные, миграции не требуют — отсутствие означает значение по умолчанию:

* `aiChatSessionsByNode` — мультисессии чата узлов-ассистентов (восстанавливается при загрузке);
* `ui.aiAgentSettings.confirmMode` — `'ask'` (по умолчанию) или `'auto'`: спрашивать ли подтверждение перед применением команд ИИ;
* `containerIsolation: { projectIds, windowIds }` — изоляция контейнеров на общем холсте. Глобальное поле, в историю Undo не входит (как и камера). Автоматически очищается при удалении изолированного контейнера, иначе на холсте не осталось бы ни одного видимого контейнера, а вместе с ним и кнопки выхода из режима;
* `historyBatch` — транзиентный маркер пакета истории.

## v12 → v13: единый источник родства (`parentId`)

**Что изменилось.** Поля `ownerId`, `ownerGap`, `homeLevel` удаляются из схемы узлов и слоёв. Родство и координатная вложенность — теперь одно и то же поле `parentId`, одно из четырёх значений: `'root'` (Главный холст), id окна уровня (сирота-якорь — прямая замена `homeLevel`), id слоя (координатная группировка) или id узла (структурный шаг на уровень вниз). Уровень сущности вычисляется по цепочке `parentId`, с шагом только на узлах (прохождение через слой уровень не меняет) — см. `docs/IDEAL_INTERACTIONS.md` §1.

**Как выполняется миграция.** `migrateToV13(state)` (`app/store/reducer.js`) проходит по `state.projects` и для каждого проекта переносит `nodes`/`layers` по трём случаям:
1. Сущность координатно вложена в реальный слой (`parentId` слоя) — контейнер остаётся как есть, `ownerId` (если был) отбрасывается: одновременно числиться в слое и структурно принадлежать другому узлу в v13 нельзя, побеждает координатный контейнер.
2. Есть живой `ownerId` и `getOwnerGap(entity) === 1` (обычное родство, без «прыжка через поколение») — `parentId` становится равен `ownerId` напрямую.
3. Иначе (истинный сирота, мёртвая ссылка на `ownerId`, или `ownerGap > 1` после очистки промежуточных уровней) — сущность «якорится» явно: `parentId` = id окна уровня с тем же `levelIndex`, что был у сущности ДО миграции (уровень 0 — компактно как `'root'`). Уровень «до» вычисляется существующим (v11) `HierarchyUtils.getLevel`, поэтому мировые координаты не смещаются ни на пиксель — меняется только то, ЧЕМ выражено родство.

Позиции, размеры, связи и любые другие поля не трогаются. Функция покрыта тестами (`app/tests/migration.test.js`), включая независимую от `hierarchy.js` эталонную реализацию целевого алгоритма уровня — чтобы проверка не зависела от кода, который сама же тестирует.

**⚠️ Отложенное включение (уточнено 2026-08-31, после Фазы 3).** `migrateToV13` реализована и протестирована, но **пока не подключена** к живой загрузке приложения (`getInitialMultiState` в `app/store/reducer.js`). `HierarchyUtils.getLevel`/`getEntityLevel` уже умеют разрешать `parentId`, указывающий на id окна уровня (Фаза 3, аддитивно — старые ветки `ownerId`/`ownerGap`/`homeLevel` не убирались, только добавлена недостающая), так что само ядро иерархии готово читать v13-данные. Но `TRANSFER_NODE` (`app/store/reducer.js`) и 4 живых места диспатча в UI (`ContextActionBar.js` ×2, `Layer.js`, `Node.js`, `OutlinerTree.js`) **продолжают писать** `ownerId`/`ownerGap`/`homeLevel` вплоть до конца Фазы 5 плана `PLAN_V12_CLEAN_HIERARCHY_AND_INTERACTIONS.md` (см. `DOCS_UPDATE_CHECKLIST.md`, «После Фазы 5» — `TRANSFER_NODE` физически удаляется только тогда). Включить миграцию раньше значило бы: пользователь загружает проект (санитизация в чистый `parentId`), затем ЛЮБОЙ перенос узла жестом снова создаёт `ownerId`-сущность поверх уже мигрированных — состояние проекта необратимо смешивается. Подключение переносится на конец Фазы 5, когда `TRANSFER_NODE` физически удалён и ownerId-поля больше никто не производит.

**Ключ хранилища:** не меняется (`architector_state_v12`), поле `formatVersion` внутри становится `13`. Легаси-ключи не удаляются.

**Обратной миграции нет.**
