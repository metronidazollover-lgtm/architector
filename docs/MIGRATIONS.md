## v11 → v12: мультипроектная обёртка

**Что изменилось.** Состояние перестало быть плоским. Прежний корень (сущности, окна уровней, камеры, история) целиком переехал внутрь одного проекта, а над ним появился слой мультипроектности:

```
{
  formatVersion: 12,
  projects: { <projectId>: { id, origin, ...все поля проекта } },
  projectOrder: [<projectId>, ...],
  activeProjectId: <projectId>,
  projectCounter: <number>,
  canvas, ui, selectedIds, ...        // глобальные поля, общие для всех проектов
}
```

**Поля проекта** (`PROJECT_FIELDS`): `projectName`, `projectColor`, `projectFontFamily`, `projectContent`, `levelWindows`, `levelViews`, `activeLevelIndex`, `levelFocusParentId`, `levelHideNeighbors`, `layers`, `nodes`, `ports`, `links`, `past`, `future`, `historyLogs`.

Ключевое следствие: **история Undo у каждого проекта своя** — отмена в одном проекте не затрагивает соседний.

**Как выполняется миграция.** `wrapFlatToMulti(flat)` заворачивает любое плоское состояние (v9/v10/v11 после соответствующих миграций) в один проект. Обратной операции нет: `mergeActiveView(m)` строит плоский ВИД активного проекта для компонентов и внутреннего редьюсера, поэтому весь прежний код продолжает читать `state.nodes` без изменений.

**Ключ хранилища:** `architector_state_v12`. Легаси-ключи не удаляются.

**Уникальность id окон.** Окна разных проектов не должны иметь общих id: они служат React-ключами и адресуют окно в выделении. Первый (мигрированный) проект сохраняет зарезервированный `lvlwin-root`, новые проекты получают сгенерированные id.

### Что НЕ переживает перезагрузку страницы (с 2026-08-24)

Массивы `past` / `future` очищаются перед записью в `localStorage`. История Undo полностью работает в пределах вкладки, но после перезагрузки страницы начинается с чистого листа. Это сознательный размен: 20 снимков сущностей на проект гарантированно переполняли квоту браузера (~5 МБ) на сколько-нибудь крупном проекте, после чего приложение навсегда оставалось в аварийном режиме сохранения.

Также не персистится транзиентное поле `historyBatch` (маркер открытого пакета истории).

### Поля, добавленные после v12

Аддитивные, миграции не требуют — отсутствие означает значение по умолчанию:

* `aiChatSessionsByNode` — мультисессии чата узлов-ассистентов (восстанавливается при загрузке);
* `ui.aiAgentSettings.confirmMode` — `'ask'` (по умолчанию) или `'auto'`: спрашивать ли подтверждение перед применением команд ИИ;
* `containerIsolation: { projectIds, windowIds }` — изоляция контейнеров на общем холсте. Глобальное поле, в историю Undo не входит (как и камера). Автоматически очищается при удалении изолированного контейнера, иначе на холсте не осталось бы ни одного видимого контейнера, а вместе с ним и кнопки выхода из режима;
* `historyBatch` — транзиентный маркер пакета истории.

## v12 → v13: единый источник родства (`parentId`)

**Что изменилось.** Поля `ownerId`, `ownerGap`, `homeLevel` удаляются из схемы узлов и слоёв. Родство и координатная вложенность — теперь одно и то же поле `parentId`, одно из четырёх значений: `'root'` (Главный холст), id окна уровня (сирота-якорь — прямая замена `homeLevel`), id слоя (координатная группировка) или id узла (структурный шаг на уровень вниз). Уровень сущности вычисляется по цепочке `parentId`, с шагом только на узлах (прохождение через слой уровень не меняет) — см. `docs/IDEAL_INTERACTIONS.md` §1.

**Как выполняется миграция.** `migrateToV13(state)` (`app/store/reducer.js`) проходит по `state.projects` и для каждого проекта переносит `nodes`/`layers` по трём случаям:
1. Сущность координатно вложена в реальный слой (`parentId` слоя) — контейнер остаётся как есть, `ownerId` (если был) отбрасывается: одновременно числиться в слое и структурно принадлежать другому узлу в v13 нельзя, побеждает координатный контейнер.
2. Есть живой `ownerId` и `getOwnerGap(entity) === 1` (обычное родство, без «прыжка через поколение») — `parentId` становится равен `ownerId` напрямую.
3. Иначе (истинный сирота, мёртвая ссылка на `ownerId`, или `ownerGap > 1` после очистки промежуточных уровней) — сущность «якорится» явно: `parentId` = id окна уровня с тем же `levelIndex`, что был у сущности ДО миграции (уровень 0 — компактно как `'root'`). Уровень «до» вычисляется существующим (v11) `HierarchyUtils.getLevel`, поэтому мировые координаты не смещаются ни на пиксель — меняется только то, ЧЕМ выражено родство.

Позиции, размеры, связи и любые другие поля не трогаются. Функция покрыта тестами (`app/tests/migration.test.js`), включая независимую от `hierarchy.js` эталонную реализацию целевого алгоритма уровня — чтобы проверка не зависела от кода, который сама же тестирует.

**✅ Включена (2026-08-31, конец Фазы 5).** `migrateToV13` подключена в `getInitialMultiState` (`app/store/reducer.js`) — применяется к загружаемому состоянию (и v12-мультипроектному, и легаси через `wrapFlatToMulti`) при каждом старте приложения. Активация стала безопасной только когда все условия совпали разом: `HierarchyUtils` понимает parentId-на-окно (Фаза 3), `TRANSFER_NODE` физически удалён и все 5 живых мест диспатча в UI переведены на `REPARENT_ENTITY` (Фаза 5) — то есть НИ ОДИН путь в приложении больше не производит `ownerId`/`ownerGap`/`homeLevel`. До этого момента включение миграции было отложено намеренно: санитизация загруженного проекта в чистый `parentId`, а следом любой перенос узла жестом снова создаёт `ownerId`-сущность поверх уже мигрированных — необратимо смешанное состояние. `ADD_NODE`/`ADD_LAYER`/`CREATE_NESTED_NODE` также переведены на чистый v13 при создании (см. коммит, переписавший `normalizeContainer`). Старые сохранения, где `ownerId`/`ownerGap`/`homeLevel` ещё встречаются, продолжают корректно читаться: `getEntityLevel`, `isEntityVisible`, `getBranchOwner` и ре-якорение при удалении/очистке уровня понимают обе формы через единый `structuralParentOf`. **С Фазы 6.5** импорт файла (`ADD_PROJECT_FROM_FILE`/`MERGE_PROJECT_FROM_FILE`) тоже приводится к чистому v13: `LOAD_STATE` внутри себя гоняет payload через `migrateToV11`/`migrateToV10`, которые не отличают v13-сироту (`parentId` прямо на узел) от старого дуализма и молча достраивают `ownerId` — оба экшена импорта дополнительно прогоняют результат через `migrateProjectEntitiesToV13`, сводя его обратно к чистому `parentId` независимо от версии исходного файла.

**Ключ хранилища:** не меняется (`architector_state_v12`), поле `formatVersion` внутри становится `13`. Легаси-ключи не удаляются.

**Обратной миграции нет.**

## v13 → v14: дорожки/окна-наборы/рамки-множества

**Что изменилось.** Уровни (общие холсты по глубине) и слои (координатный контейнер, он же владелец) уступают место трём сущностям — см. `docs/LANES_MODEL.md`. Единственная структура родства сохраняется и упрощается до `parentId ∈ {'root', nodeId}` — сирота-якорь (`parentId` = id окна уровня) и id слоя как значение `parentId` больше не встречаются вовсе. В схеме проекта: `layers` → `frames` (множество-членство `members`, без `position`/`parentId`), `levelWindows` + `levelViews` → `windows` (набор дорожек `lanes`, своя камера). Поля `levelHideNeighbors`, `levelFocusParentId`, `activeLevelIndex` удаляются без замены — переноса семантики не требуется (см. `docs/LANES_MODEL.md` §2.5).

**Как выполняется миграция.** `migrateProjectEntitiesToV14(proj)` (`app/store/reducer.js`) предполагает на входе уже чистый v13-проект (без `ownerId`/`ownerGap`/`homeLevel` — их снимает `migrateProjectEntitiesToV13`, вызываемая раньше в цепочке, а не внутри этой функции) и идёт по шагам плана (§2.6):
1. Сирота-якорь (`parentId` = id окна уровня, у узла ИЛИ у слоя) → `parentId: 'root'`. Домашняя глубина не воспроизводится — сохраняется только ветка потомков, а не точная старая позиция в иерархии (решение §0.4.7 плана: «сироты — в корень проекта, ветка сохраняется»). Это осознанное упрощение относительно того, как аккуратно v12→v13 сохраняла точный уровень через явный якорь — у v14 нет отдельного поля для «домашней глубины», а плодить новую сущность специально под сирот старых файлов сочли неоправданным.
2. Каждый слой становится рамкой. Структурный родитель узла или рамки — первый узел (или `'root'`) при подъёме по цепочке `parentId` ЧЕРЕЗ слои (та же семантика обхода, что у `HierarchyUtils.getLocalPosition` — слой проходной, узел терминальный). Позиция узла копит смещения всех пройденных слоёв. Вложенный слой (слой внутри слоя) даёт узлу членство сразу в ОБЕИХ рамках — внутренней и внешней, — так bbox внешней рамки естественно охватывает внутреннюю, воспроизводя старую картинку вложенных слоёв без вложенности самих рамок (рамки в v14 родства не имеют, только множество-членство).
3. Порты слоёв не трогаются — `ports[].nodeId` уже равен id слоя, а id слоя при превращении в рамку не меняется.
4. Каждое старое окно уровня `k` даёт новое окно с `lanes` = все узлы НОВОЙ (уже посчитанной на шагах 1–2) глубины `k−1`, у которых есть дети; окно уровня 0 получает `lanes: ['root']` безусловно. Окно, у которого после этого не набралось ни одной дорожки, не создаётся (`normalizeWindows` схлопывает пустые). Камера окна берётся из `levelViews[wid].innerOffset/innerZoom` → `windows[wid].camera.offset/zoom`.
5. `formatVersion = 14`.

`normalizeWindows(rawWindows, nodes)` — защитная чистка окон, аналог `normalizeLevelWindows`, но БЕЗ авто-создания окна на каждую глубину (в v14 окно открывается только явным действием пользователя, см. `docs/LANES_MODEL.md` §10): убирает из `lanes`/`hidden` ссылки на дорожки несуществующих узлов и схлопывает окно, опустевшее после этой чистки.

Функции покрыты тестами (`app/tests/migration.test.js`), включая независимую от `migrateProjectEntitiesToV14` эталонную реализацию структурного родителя (та же дисциплина, что и у `migrateToV13`-тестов), фикстуры: v11-файл с `ownerGap` через полную цепочку `migrateToV13`, v13-сирота-якорь напрямую на окно, слой-в-слое, слой с портами.

**✅ Включена (конец Фазы 4, см. «Отчеты, аудиты, планы/Lanes_v14/PLAN_V14_LANES.md» §7.14).** `getInitialMultiState` строит состояние композицией `migrateToV14(migrateToV13(wrapFlatToMulti(...)))` — живая загрузка теперь всегда v14-форма (`nodes`/`frames`/`windows`, без `layers`/`levelWindows`/`levelViews`). Активация стала безопасной, когда совпали разом все условия: `hierarchy.js` понимает дорожки/окна/рамки (Фаза 2), обработчики действий в `reducer.js` переведены на них (Фаза 3), UI-компоненты (`Frame.js`/`Lane.js`/`LaneWindow.js`) заменили `Layer.js`/`LevelWindow.js` (Фаза 4) — то есть ни один живой путь в приложении больше не производит и не ожидает `layers`/`levelWindows`. **Фаза 6** физически удалила из `hierarchy.js`/`reducer.js` весь v13-only код (геометрия окон уровней, «глаз» веток, старый резолвер Drag&Drop и т.д.), не имевший живого пути вызова, и старые компоненты `Layer.js`/`LevelWindow.js` как файлы. `migrateToV13`/`normalizeLevelWindows`/`migrateProjectEntitiesToV13` (и их прямые зависимости в `hierarchy.js` — `getLevel`/`getOwnerGap`/`getMaxProjectLevel`/`getRawChainSum`) остаются постоянным звеном цепочки миграций — старые сохранения по-прежнему читаются и доводятся до v14 на лету, независимо от того, из какой версии реально пришёл файл (`LOAD_STATE`, `ADD_PROJECT_FROM_FILE`, `MERGE_PROJECT_FROM_FILE` — см. §7.15 плана).

**Ключ хранилища:** не меняется (`architector_state_v12`), поле `formatVersion` внутри — `14`.

**Обратной миграции нет.**
