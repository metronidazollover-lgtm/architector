# Инструкции для ИИ-ассистентов (AGENTS.md)

Данный документ содержит ключевые архитектурные правила, спецификацию структуры и стандарты разработки для приложения **Architector**. Все ИИ-модели, работающие с этой кодовой базой, должны строго соблюдать изложенные здесь соглашения.

---

## 🏛️ Архитектурная философия (Zero-Build)

1. **Отсутствие бандлера и сборки (Zero-Build):**
   * Приложение работает напрямую в браузере без Webpack, Vite, Rollup или Babel CLI.
   * Все глобальные библиотеки (React 18, ReactDOM, Babel Standalone, Tailwind CSS Play CDN, Lucide Icons) подключаются через CDN в `app/index.html`.
   * Компоненты подключаются тегами `<script type="text/babel" src="...">` в `app/index.html`.
   * **КРИТИЧЕСКОЕ ПРАВИЛО:** В файлах компонентов **НЕЛЬЗЯ использовать синтаксис ES-модулей `import` / `export`** для браузерного скриптинга. Все компоненты и утилиты объявляются в общем глобальном скоупе Babel.

2. **Двойной экспорт утилит (Browser + Node.js):**
   * Файлы `app/utils/geometry.js`, `app/utils/hierarchy.js` и `app/store/reducer.js` исполняются как в браузере, так и в средах без DOM (в тестовом раннере `node:test`).
   * В конце каждого такого файла используется схема двойного экспорта:
     ```js
     if (typeof module !== 'undefined' && module.exports) {
         module.exports = GeometryUtils;
     } else {
         window.GeometryUtils = GeometryUtils;
     }
     ```

## 📐 Модель данных v13 и Инварианты

1. **Формат сохранения (`formatVersion: 13`) — пространственные уровни:**
   * Каждый уровень иерархии — отдельное окно (`levelWindows`, ключ — стабильный id окна, номер уровня — поле `levelIndex`; окно L0 — `lvlwin-root`). Камеры окон живут в `levelViews` (вне истории Undo).
   * **Единый источник правды — `parentId`.** У каждой сущности (узла, слоя) ровно один родитель — одно из четырёх значений: `'root'` (сокращение для окна L0), id окна уровня (сирота-якорь, привязка к конкретному уровню N>0 — прямая замена удалённого `homeLevel`), id слоя (координатная группировка, уровень не меняется) или id узла (структурный шаг — сущность живёт на СЛЕДУЮЩЕМ уровне). Уровень сущности вычисляется рекурсивным подъёмом по цепочке `parentId` (`HierarchyUtils.getEntityLevel`, правило семантического шага): слой — проходной (без инкремента), узел — шаг +1, окно — терминальный случай (уровень читается из `levelIndex` напрямую). Подробности и математика — `docs/IDEAL_INTERACTIONS.md` §1.
   * **Полей `ownerId`, `ownerGap`, `homeLevel` в новых сущностях больше нет** — ни один живой путь создания (`ADD_NODE`, `ADD_LAYER`, `CREATE_NESTED_NODE`, `REPARENT_ENTITY`) их не заводит. Старые сохранения (v11/v12), где эти поля ещё встречаются, продолжают читаться корректно: `getEntityLevel`/`isEntityVisible`/`getBranchOwner` и ре-якорение при удалении/очистке уровня понимают ОБЕ формы через единый `structuralParentOf` (ownerId, если есть, иначе parentId-на-узел) — жёсткой миграции существующих локальных сохранений при загрузке пока нет (`migrateToV13` реализована и покрыта тестами, но её включение в `getInitialMultiState` — следующий шаг).
   * `position` локальна холсту уровня (или слою-контейнеру), как и раньше. Мировые координаты — через `HierarchyUtils.getWorldTransform` / `getPortWorldPosition`.
   * **Режим Drag&Drop (`ui.dragDropMode`).** Смысл не изменился — предохранитель от случайных межуровневых переносов. Выключен (дефолт при каждой загрузке): перетаскивание клампится рамкой своего окна, доступна только группировка в слои своего уровня. Включён: сквозной перенос, вложение слоя в слой, перенос между уровнями. Резолвер целей — `HierarchyUtils.getDropTarget` (контуры для узлов/слоёв, указатель для окон, приоритет узел → слой → окно, потомки исключены через `isDescendantOf`/`hasAncestorIn`); дроп применяет `REPARENT_ENTITY` после вопроса-подтверждения (`buildTransferConfirmText`), отмена — `RESTORE_ENTITIES`. Два режима переноса: `mode: 'deep'` (по умолчанию, ветка целиком) и `mode: 'shallow'` (зажатый `Alt` во время перетаскивания в `Node.js`/`Layer.js` — вырывание узла, прямые дети усыновляются прежним родителем с авто-раздвижкой `GeometryUtils.findFreePosition`; режим читается живо весь жест, не только на старте). Выталкивание слоёв друг от друга (`GeometryUtils.resolveLayerCollision`, в `Layer.js`) на время жеста безусловно отключено при включённом тумблере — иначе слой не вложить в слой. Переносимые элементы на время жеста рендерятся поверх окон (оверлей в `Canvas.js`, `state.dragGesture`) — набор id для оверлея расширяется их parentId-вложенными потомками (`HierarchyUtils.hasAncestorIn`), иначе узел, назначенный на переносимый слой, визуально пропадал бы в момент пересечения границы окна.
   * Удаление уровня N≥1 (`REMOVE_LEVEL_WINDOW`) сдвигает нижние уровни вверх («следующий становится предыдущим»): потомки удалённых узлов пере-подчиняются родителю удалённого напрямую по `parentId` («внук — деду»). Внук, чья дистанция до деда растянута (родитель сам был сиротой-якорем через несколько уровней — только для ещё не мигрированных `ownerId`-цепочек), не теряется: становится явным якорем на своём сдвинутом уровне, а не съезжает на уровень 0. Окна сохраняют id/рамку/камеру, мастер-порты перенумеровываются. Главный холст (L0) удаляется экшеном `REMOVE_ROOT_CANVAS`, через `REMOVE_LEVEL_WINDOW { index: 0 }`, крестик `[X]` на шапке окна или клавишу `Delete` (при наличии Уровня 1 окно уровня 1 становится Главным холстом). Если окно L0 — единственное в проекте, при удалении выдаётся подтверждение и удаляется сам проект (`REMOVE_PROJECT`).
   * **Названия уровней и бейджи:** Все новые окна создаются с единым именем по умолчанию `"New level"`. В шапке каждого окна выводится унифицированный бейдж с иконкой папки и номером уровня: `[ 📁 0 ]`, `[ 📁 1 ]` и т.д.
   * Очистка уровня (`CLEAR_LEVEL_WINDOW`) удаляет ТОЛЬКО сущности этого уровня: потомки выживают на своих уровнях (уровни НЕ сдвигаются — окно остаётся), пере-подчиняясь ближайшему живому предку по `parentId`; без живых предков (или при той же растянутой дистанции, что и выше) — становятся сиротами-якорями на своём (неизменном) уровне. Очистка L0 делает всех детей уровня 1 сиротами. Полный сброс содержимого всех уровней — отдельный экшен `CLEAR_PROJECT`.

2. **Ключи словарей:**
   * В объектах `nodes`, `layers`, `ports`, `links` ключ в словаре **ОБЯЗАТЕЛЬНО** совпадает с `entity.id` (например, `nodes["node-1"].id === "node-1"`).

3. **Форма нод (`shape`):**
   * Все узлы имеют стандартизированную прямоугольную форму `shape: "rectangle"`.

4. **Предотвращение двойного смещения:**
   * При перемещении родителя его потомки перемещаются автоматически за счет относительных координат. При массовом выделении проверяется `hasSelectedAncestor`, чтобы дочерние элементы не сдвигались дважды.

5. **Разделение явного выделения и визуальной подсветки:**
   * Обработчики событиий (`handleMouseDown`) и логика Redux проверяют `isExplicitlySelected = state.selectedIds.includes(id)`.
   * Визуальный рендеринг компонентов (`isSelected`) учитывает косвенное подсвечивание соединенных сетей связей/портов/узлов. `selectedIds` при клике хранит строго выбранную сущность для единичного редактирования свойств.

6. **Порядок скриптов в `index.html`:**
   * Скрипты подключаются strictly по цепочке: `utils/` → `store/` → `components/` → `app.js`. Новый компонент обязательно регистрируется в `app/index.html`.

7. **Визуализация портов и сетей связей:**
   * Стандартный размер порта: `w-3 h-3` (12px).
   * При выделении или подсвечивании соединенной сети порт масштабируется с коэффициентом `scale-[2.1]`.
   * **Порты и связи слоёв (2026-08-28).** Слой — полноправный участник графа связей наравне с узлом: несёт порты на всех 4 гранях (клик по грани в режиме `add-port`; Shift+драг скользит порт по периметру слоя, как у узла), соединяется связями Слой ↔ Слой и Слой ↔ Узел. Хост-сущность порта разрешается полиморфно (`state.nodes[id] || state.layers[id]`) в `getPortWorldPosition`/`getCrossLinksByLevel` (`hierarchy.js`) и в компонентах `Port.js`/`Link.js`. Удаление слоя каскадно удаляет его порты и подключённые связи. Формат хранения — `formatVersion: 13`.

8. **Управление свойствами через верхнюю контекстную панель (Context Action Bar):**
   * Все свойства узлов (цвет, значок, медиа-ссылка, перенос на слой, группа, привязка к сетке, удаление, типографика) настраиваются через единую верхнюю контекстную панель свойств.


9. **Динамический авторесайз и перенос текста (Live Auto-Sizing):**
   * При инлайн-редактировании имени (`name`) и описания (`content`) размеры узла пересчитываются мгновенно на лету (`onChange`, `skipHistory: true`).
   * Для заголовка поддерживается перенос строк (`break-all`, `nameLines`) с автоматическим увеличением высоты шапки и узла до ширины A4 (794px).
   * В обычном авторежиме полосы прокрутки отсутствуют, а кастомный скроллбар (`custom-scrollbar`) появляется только при ручном сжатии узла пользователем (`userResized: true`).

## 🤖 Спецификация и протокол управления для внешних ИИ-Агентов (API & Function Calling Protocol)

Данный раздел является **официальной спецификацией для подключенных внешних ИИ-агентов (LLM через OpenAI API, Anthropic Claude, Gemini или локальные нейросети)**, которые генерируют или модифицируют графы в приложении Architector.

### 1. Формат выполнения команд

Любые изменения графа со стороны ИИ-агента передаются в виде **массива Redux-экшенов в JSON-блоке** в конце текстового ответа:
```json
[
  { "type": "ACTION_NAME", "payload": { ... } }
]
```

### 2. Спецификация сущностей и типов данных

#### 🎨 Слои (`layer`)
Слой — это визуальный фрейм-контейнер для группировки узлов.
* `id` *(string, обязательный)*: уникальный ID (например `"layer-ui"`).
* `name` *(string, обязательный)*: заголовок слоя.
* `content` *(string)*: краткое описание назначения слоя.
* `color` *(string)*: HEX-цвет границы и фона шапки (например `"#0284c7"`).
* `fontFamily` *(string, опционально)*: гарнитура шрифта (например `"Montserrat, sans-serif"`).
* `fontSize` *(number, опционально)*: размер шрифта заголовка (11..24, по умолчанию 14).
* `position` *({x: number, y: number}, обязательный)*: относительно родителя.
* `size` *({w: number, h: number}, обязательный)*: размеры (рекомендуется от 500x400px).
* `parentId` *(string)*: ID родительского контейнера (по умолчанию `"root"`).
* `snapToGrid` *(boolean)*: удержание сетки (всегда `true`).

#### 📦 Узлы (`node`)
Узел — центральный компонент логики или структуры.
* `id` *(string, обязательный)*: уникальный ID (например `"node-viewport"`).
* `name` *(string, обязательный)*: название узла.
* `content` *(string)*: текстовое или маркдаун описание.
* `color` *(string)*: HEX-цвет фона шапки узла.
* `fontFamily` *(string, опционально)*: гарнитура шрифта (например `"Fira Code, monospace"`).
* `fontSize` *(number, опционально)*: кегль шрифта (11..24, по умолчанию 14, динамически масштабирует шапку и узел).
* `position` *({x: number, y: number}, обязательный)*: координаты относительны родителя.
* `size` *({w: number, h: number}, обязательный)*: габариты (автоподстройка по умолчанию, базовая ширина 220-300px).
* `parentId` *(string)*: ID родительского контейнера (`"root"`, ID слоя или ID узла).
* `shape` *(string)*: форма узла — `"rectangle"` (по умолчанию).
* `type` *(string)*: `"default"` (обычный) или `"ai-agent"` (интерактивный ИИ-копилот).
* `icon` *(string, опционально)*: иконка Lucide (`"icon-box"`, `"icon-bot"`) или эмодзи (`"🤖"`).
* `mediaUrl` *(string, опционально)*: URL картинки для медиа-карточки.
* `mediaHeight` *(number, опционально)*: высота картинки в пикселях (например `80`).

#### 🔌 Порты (`port`)
Точка привязки линий на гранях узла ИЛИ слоя — слой полноправно участвует в графе связей наравне с узлом (см. §7 в разделе «Модель данных»).
* `id` *(string, обязательный)*: уникальный ID (например `"port-vp-out"`).
* `nodeId` *(string, обязательный)*: ID сущности-владельца — узла **или слоя**. Несмотря на имя поля (легаси), значением может быть как `node.id`, так и `layer.id`.
* `type` *(string)*: `"input"` (вход) или `"output"` (выход).
* `edge` *(string)*: грань узла — `"left"`, `"right"`, `"top"`, `"bottom"`.
* `position` *(number 0.0..1.0)*: смещение вдоль грани (0.5 = середина).
* `name` *(string)*: подпись порта.
* `content` *(string, опционально)*: описание передаваемых данных порта.
* `fontFamily` *(string, опционально)*: гарнитура шрифта.
* `fontSize` *(number, опционально)*: размер шрифта (по умолчанию 12).
* `color` *(string)*: HEX-цвет точки привязки.

#### ⚡ Связи (`link`)
Линии, соединяющие порты. Так как порт может принадлежать и узлу, и слою, связь допустима в любой комбинации: Узел ↔ Узел, Слой ↔ Слой, Узел ↔ Слой.
* `id` *(string, обязательный)*: уникальный ID (например `"link-ui-store"`).
* `sourcePortId` *(string, обязательный)*: ID порта-источника.
* `targetPortId` *(string, обязательный)*: ID порта-приемника.
* `name` *(string)*: подпись связи (например `"HTTP Dispatch"`).
* `content` *(string, опционально)*: описание назначения связи.
* `linkStyle` *(string)*: `"orthogonal"` (прямые углы) или `"bezier"` (плавная кривая).
* `fontFamily` *(string, опционально)*: гарнитура шрифта.
* `fontSize` *(number, опционально)*: размер шрифта (по умолчанию 12).
* `color` *(string)*: HEX-цвет линии.
* `context` *(string)*: контекст отображения (обычно совпадает со слоем или `"root"`).

### 3. Математика координат (v13)

1. **Если `parentId === 'root'` или id окна уровня:** координаты `position` локальны холсту того уровня (уровень определяется цепочкой `parentId`, для сироты-якоря — напрямую `levelIndex` окна). Для уровня 0 это координаты внутри окна Главного холста.
2. **Если `parentId` — id слоя:** координаты считаются от левого верхнего угла слоя-контейнера. Безопасный внутренний диапазон для слоя 600×400: `x: 30..350`, `y: 80..280`.
3. **Родитель узла — единственное поле `parentId`**, назначается при создании и при `REPARENT_ENTITY`; расщепления на `parentId`/`ownerId` больше нет. Узел с родителем-узлом уровня N живёт на уровне N+1 и отображается в окне этого уровня.

#### Мультипроектность (v12)

| Экшен | Payload | Описание |
|---|---|---|
| `ADD_PROJECT` | `{ name? }` | Создать пустой проект правее существующих и сделать его активным |
| `ADD_PROJECT_FROM_FILE` | данные проекта | Импорт файла как ДОБАВЛЕНИЕ проекта (не замена) |
| `REMOVE_PROJECT` | `{ id? }` | Удалить проект целиком. Необратимо: межпроектной истории нет |
| `SET_ACTIVE_PROJECT` | `id` | Сделать проект активным (сбрасывает выделение) |
| `FOR_PROJECT` | `{ projectId, action }` | Доставить любой внутренний экшен в КОНКРЕТНЫЙ проект, не делая его активным |
| `LOAD_GLOBAL_STATE` | данные ВСЕГО рабочего пространства (Фаза 6.4) | Заменяет `projects`/`projectOrder`/`activeProjectId`/`projectCounter`/`crossProjectLinks` целиком. Деструктивно — необратимо |
| `MERGE_PROJECT_FROM_FILE` | данные проекта (Фаза 6.5) | Слить файл В АКТИВНЫЙ проект: каждая сущность получает свежий id, коллизии позиций на корне уровня разводятся автоматически |

**`ADD_PROJECT_FROM_FILE`/`MERGE_PROJECT_FROM_FILE` прогоняют файл через `migrateProjectEntitiesToV13`.** `LOAD_STATE` внутри себя вызывает `migrateToV11`/`migrateToV10` — они не умеют отличить «сироту v13 с `parentId` прямо на узел» от старого дуализма `parentId`/`ownerId` и достраивают `ownerId` там, где в файле его не было. Оба экшена дополнительно прогоняют результат `LOAD_STATE` через `migrateProjectEntitiesToV13`, сводя это обратно к чистому `parentId` — независимо от того, из какой версии реально пришёл файл.

**`MERGE_PROJECT_FROM_FILE`: ремап id и слияние окон.** Каждый узел/слой/порт/связь файла получает свежий id (карта `oldId -> newId`); внутренние ссылки (`parentId`, `nodeId` порта, `sourcePortId`/`targetPortId`, ключи `proxyOverrides`, `portId` внутри `externalGateways`) переписываются через неё. Окна уровней: то же `levelIndex`, что уже есть в активном проекте — сущности сливаются В НЕГО; отсутствующий уровень — заводится новое окно (та же логика роста глубины, что у кросс-проектного `REPARENT_ENTITY`). **Главный холст файла (`'root'`) мержится в Главный холст активного проекта ЛИТЕРАЛОМ `'root'`, а не явным id его окна** — иначе `GeometryUtils.resolveContextCollisions` (группирует контекст СТРОКОЙ `parentId`) не увидел бы общий контекст между исходным содержимым активного проекта (адресует себя литералом) и только что слитым (адресовало бы себя явным id окна) и не развёл бы коллизии между ними. Импортированные `externalGateways` (portId уже перемаппленный) оседают в `pendingGateways` активного проекта, дальше — обычная `reconcilePendingGateways`: если совпадающая половина штекера лежит в ДРУГОМ проекте — связь пересобирается сразу.

**UI выбора варианта (`ContextActionBar.js`/`handleImportProject`).** Для файла, у которого нет `kind: 'global'`: `window.confirm` — ОК = слить с активным (`MERGE_PROJECT_FROM_FILE`), Отмена = добавить как новый проект (`ADD_PROJECT_FROM_FILE`, поведение по умолчанию, как и раньше). Оба «глобальных» и «слитных» экшена диспатчатся через `rawDispatch`, а не через локально-обёрнутый `dispatch` компонента — тот заворачивает большинство экшенов в `FOR_PROJECT`, адресуя одно-проектному `reducer`, у которого нет таких `case`.

**Глобальный экспорт/импорт рабочего пространства (Фаза 6.4).** `handleExportWorkspace`/`handleImportWorkspace` (`ContextActionBar.js`) — в отличие от `handleExportProject`/`ADD_PROJECT_FROM_FILE` (один проект, режим «добавить»), эти работают с ВСЕМ пространством разом и в режиме «заменить»: экспорт сериализует `{ projects, projectOrder, activeProjectId, projectCounter, crossProjectLinks, canvas }` (только так можно унести кросс-проектные связи — они не принадлежат ни одному проекту по отдельности); импорт диспатчит `LOAD_GLOBAL_STATE` через `rawDispatch` (НЕ через локально-обёрнутый `dispatch` этого компонента — тот на действиях, отличных от списка исключений, заворачивает всё в `FOR_PROJECT`, адресуя внутреннему одно-проектному `reducer`, у которого просто нет такого case, — экшен обязан попасть в `multiReducer` напрямую). `sanitizeLoadedProjects(rawProjects, rawProjectOrder)` — санитизация, общая с `getInitialMultiState` (нормализация окон/связей, чистая история): вынесена в `reducer.js`, чтобы оба пути (загрузка из `localStorage` при старте и импорт файла) не расходились. После загрузки — `reconcilePendingGateways` (на случай, если в самом файле уже лежали обе половины разорванной связи). UI спрашивает подтверждение ДО диспатча (`window.confirm`, деструктивная операция).

**Неактивные проекты полностью интерактивны (PLAN V6, 2026-08-28).** Узел, слой, порт и связь чужого (неактивного) проекта на общем холсте кликабельны, выделяются, редактируются инлайн и перетаскиваются наравне с активным — ограничение `pointer-events: none` снято. Клик по элементу неактивного проекта мягко (по `onClick`, не по `mousedown`, чтобы не срывать жест) синхронизирует активный проект для верхних панелей.

**Как компоненты холста получают состояние своего проекта (`ProjectContext`).** Компоненты холста (`Node.js`, `Port.js`, `Layer.js`, `Link.js`) НЕ читают активный проект напрямую — у них есть проектно-адресный слой поверх `Store.js`:
* `ProjectContext` — React-контекст с `projectId` того окна на холсте, в котором рендерится компонент (`Canvas.js` оборачивает каждое окно и Drag-оверлей в `<ProjectContext.Provider value={projectId}>`).
* `getProjectFlatView(projectId)` — плоский вид ЛЮБОГО проекта (не только активного), кэшированный по стабильной ссылке на `state.projects[projectId]`.
* `useProjectSelector(selector)` / `useProjectDispatch()` — берут `projectId` из `ProjectContext`; запись в проект, отличный от активного, автоматически заворачивается в `FOR_PROJECT`.
* `useProjectStore()` (2026-08-29) — аналог `useStore()` (весь плоский вид проекта + `dispatch`, без селектора), но привязанный к `ProjectContext`. Используется в `AIAgentNodeContent.js`: узел-ассистент рендерится внутри `NodeView` конкретного проекта и обязан читать/писать СВОЙ проект, даже если активен другой. До этой правки узел использовал `useStore()` и в неактивном проекте молча читал и менял активный проект — баг того же семейства, что чинили для окон уровней.

Панели (`Toolbar.js`, `Library.js`, `ContextActionBar.js`) на проектно-адресный слой НЕ переведены — используют обычные `useStore()`/`useSelector()`/`useDispatch()` и осознанно работают только с активным проектом.

#### Кросс-проектные связи (Фаза 6.1) и штекеры разрыва (Фаза 6.2)

| Экшен | Payload | Описание |
|---|---|---|
| `ADD_CROSS_PROJECT_LINK` | `{ id?, sourceProjectId, sourcePortId, targetProjectId, targetPortId, name?, color?, linkStyle? }` | Создать связь между портами ДВУХ РАЗНЫХ проектов. Обрабатывается в `multiReducer` напрямую (не делегируется) |
| `REMOVE_CROSS_PROJECT_LINK` | `id` | Удалить кросс-проектную связь |
| `UPDATE_CROSS_PROJECT_PROXY_PORT` | `{ linkId, windowId, edge, fraction }` | Аналог `UPDATE_PROXY_PORT` для связи из `crossProjectLinks` (пишет в `link.proxyOverrides[windowId]`, а не в `state.links`) |
| `UPDATE_PENDING_GATEWAY_PROXY` | `{ linkId, edge, fraction, skipHistory? }` | Ручное положение прокси НЕПРИМИРЁННОГО штекера (`project.pendingGateways[linkId]`) — проектное поле, участвует в обычном Undo проекта |

**`state.crossProjectLinks`** — глобальное поле (НЕ `PROJECT_FIELD`), форма как у обычной связи + `sourceProjectId`/`targetProjectId`. Живёт ВНЕ истории Undo обоих проектов, как `canvas`/`containerIsolation`: связь трогает ДВА проекта разом, а `past`/`future` — раздельная история КАЖДОГО проекта, единого места для одного атомарного шага здесь нет.

**Резолвер цели `Port.js` видит порты всех проектов.** Поиск ближайшего порта под курсором при отпускании связи сначала ищет в своём проекте (как раньше), затем — если ничего не найдено — сканирует `state.projectOrder` остальных проектов через `getProjectFlatView(pid)` (окна всех проектов уже на общем холсте в одной мировой системе координат). Найденный порт в чужом проекте диспатчит `ADD_CROSS_PROJECT_LINK` вместо `ADD_LINK`. Дроп на чужой прокси-порт, узел или пустое место — вне охвата этого шага (создаёт только связь порт-в-порт).

**Прокси-геометрия расширена на границу проекта (`hierarchy.js`).** `buildWindowProxyGeometry(win, winIndex, item, edge, fraction)` — чистая формула точки на рамке, вынесенная из `getProxyPortsForWindow` (`makeProxy` теперь тонкая обёртка над ней). `getExternalProxyPortsForWindow(windowId, projectId, multiState)` — та же геометрия для `crossProjectLinks`: грань выбирается сравнением МИРОВЫХ центров двух окон по доминирующей оси (между проектами нет общего «уровня», сравнивать нечего). `getExternalProxyForLink(linkId, windowId, projectId, multiState)` — точечный поиск, аналог `getProxyForLink`. `LevelWindow.js` подмешивает внешние прокси к внутренним в `proxyPorts` (единый список, единый рендер внутреннего отрезка); `Canvas.js`'s `CrossProjectLinkLayer` — новый слой магистралей, ОДИН на холст (не на проект, в отличие от `CrossLevelLinkLayer`), резолвящий обе стороны через `getExternalProxyForLink`. Единственное визуальное отличие от обычной межуровневой связи — CSS-класс `cross-project-link-pulse` (keyframe в `index.html`) на обоих сегментах и на самой точке прокси.

**Удаление проекта демоутит связь, а не теряет её.** `applyRemoveProject` для каждой `crossProjectLinks`-записи, задевающей удаляемый проект: если проект на другой стороне ещё жив — запись переносится в его `pendingGateways[linkId]` (снимок направления, удалённого порта/проекта по имени, грани/доли прокси на момент разрыва) вместо молчаливого удаления; если гибнут обе стороны — запись пропадает совсем. `pendingGateways` — `PROJECT_FIELD`.

**`externalGateway`: локальный экспорт и автовосстановление (Фаза 6.2).** `handleExportProject` (`ContextActionBar.js`) добавляет в файл `externalGateways` — по одной записи на каждую `crossProjectLinks`, задевающую экспортируемый проект, с тем же `linkId`, что был у живой связи. При импорте («добавить как новый проект», `ADD_PROJECT_FROM_FILE`) эти записи копируются в `pendingGateways` нового проекта как есть — id портов внутри одного файла коллизий не создают. `reconcilePendingGateways(m)` (вызывается после `ADD_PROJECT_FROM_FILE` и после демоушена в `applyRemoveProject`) группирует `pendingGateways` ВСЕХ проектов по `linkId`; там, где нашлась ровно одна пара с противоположными `direction` ('out'+'in') — синтезирует живую `crossProjectLinks`-запись и убирает оба штекера. **Сверка идёт только по `linkId`, БЕЗ проверки совпадения `remoteProjectId`** — при повторном импорте контрагент получает СВЕЖИЙ `projectId` (`newProjectId()`), а уцелевшая сторона продолжает помнить СТАРЫЙ, уже удалённый; именно нестабильность `projectId` между экспортом/импортом и есть причина, почему опорный идентификатор — `linkId` связи, а не id проекта на другом конце. Непримирённый штекер рисуется как маркер разрыва на рамке окна — `HierarchyUtils.getPendingGatewayProxiesForWindow(windowId, projectId, multiState)` (грань/доля берутся из самой записи, НЕ пересчитываются — сравнивать не с чем, второе окно не загружено), только внутренний отрезок, без магистрали (`CrossProjectLinkLayer` штекеры не рисует). Тултип у штекера — `«{remotePortName}» в проекте «{remoteProjectName}» (сейчас не загружен)`.

#### Кросс-проектный перенос сущностей (Фаза 6.3)

Перенос узла/слоя (и его ветки) между проектами живым Drag&Drop — не поповером и не отдельным экшеном создания, а тем же самым жестом, что уже переносит сущности внутри проекта: неактивные проекты и так полностью рендерятся на общем холсте в единой мировой системе координат, так что задача сводится к расширению резолвера цели на сканирование всех проектов, а не к новому UI.

- **`HierarchyUtils.getDropTarget(draggedIds, pointerWorld, state, opts, sourceState?)`** — 5-й параметр (по умолчанию `null` → тот же `state`, поведение не меняется): `dragged`/`dragRects`/`draggedLevels`/`unsupportedMixedLayer` считаются из `sourceState` (проект перетаскиваемых сущностей), кандидаты цели (`nodes`/`layers`/`levelWindows`) — по-прежнему из `state` (проект под курсором). «Своё окно» (`isMove`) определяется буквальным совпадением id окна (глобально уникален между проектами), а не номера уровня — у кросс-проектного дропа номер уровня цели может случайно совпасть с номером уровня источника, оставаясь другим окном.
- **`HierarchyUtils.canReparentTo(entityId, targetParentId, nodes, layers, levelWindows, entityDicts?)`** — 6-й параметр `{nodes, layers}` сущности, если отличаются от целевых словарей: существование `entityId` проверяется в НИХ, цикл — пропускается (геометрически невозможен между двумя разными деревьями).
- **`HierarchyUtils.computeDropPositions(ids, win, state, sourceState?)`** — аналогично: мировые координаты переносимых берутся из `sourceState`, камера/зум целевого окна — из `state`.
- **`HierarchyUtils.getDropTargetAcrossProjects(draggedIds, pointerWorld, multiState, sourceProjectId, opts)`** — обёртка над `getDropTarget`: для каждого `pid` из `multiState.projectOrder` (кроме скрытых изоляцией) вызывает его с `getProjectFlatView(pid)` в роли `state` и `getProjectFlatView(sourceProjectId)` в роли `sourceState`; лучший результат — по приоритету node > layer > window, валидный побеждает невалидный. Возвращает тот же формат, что `getDropTarget`, плюс `projectId` найденной цели.
- **Жест в `Node.js`/`Layer.js`:** `computeTarget` вызывает `getDropTargetAcrossProjects` вместо `getDropTarget` (проект перетаскиваемой сущности уже активен — форсирован на mousedown). На `mouseup`, если `target.projectId` отличается от исходного проекта — `REPARENT_ENTITY` получает дополнительные `sourceProjectId`/`targetProjectId`; окно-цель резолвится из `getProjectFlatView(target.projectId)`, а не из своего `st`. Deep/Shallow (Alt) работают одинаково в обоих случаях — Shallow переприкрепляет детей к деду ВНУТРИ исходного проекта до того, как верхняя сущность уезжает.
- **`applyCrossProjectReparent(m, payload)`** в `multiReducer` — перехватывает `REPARENT_ENTITY`, когда `sourceProjectId`/`targetProjectId` заданы и различны (иначе — как раньше, `delegateToActiveProject`). Собирает ветку (сущность + все структурные потомки по `parentId`, их порты, полностью внутренние связи) из исходного проекта, при Shallow — сперва переприкрепляет прямых детей к деду; вставляет в целевой проект (`findFreePosition` на корне `targetParentId`, либо явная позиция под курсором); `crossProjectLinks`/`pendingGateways`, чей порт уехал вместе с веткой, переписываются на новый `projectId`. **Не участвует в Undo ни одного из проектов** (как и создание/удаление `crossProjectLinks`).
- **Подсветка цели по `projectId`.** `dragGesture` — глобальное поле, видно во всех проектах разом; `Node.js`/`Layer.js`/`LevelWindow.js` при матчинге `dragGesture.target` теперь также сверяют `target.projectId` с собственным — иначе гипотетическое совпадение id между двумя проектами подсветило бы не тот узел.
- **`buildTransferConfirmText(ids, target, state, mode, targetState?)`** — 5-й параметр для текста подтверждения, когда цель в другом проекте (иначе имена/уровень резолвились бы из чужих словарей); добавляет «(проект «X»)» к описанию цели.

#### Выделение контейнеров и их изоляция

| Экшен | Payload | Описание |
|---|---|---|
| `TOGGLE_CONTAINER_ISOLATION` | `{ kind: 'project'\|'window', id }` | Включить/снять изоляцию контейнера на общем холсте |
| `SET_CONTAINER_ISOLATION` | `{ projectIds, windowIds }` | Задать набор изолированного целиком |
| `CLEAR_CONTAINER_ISOLATION` | — | Снять изоляцию контейнеров |

**Адресация в `selectedIds`.** Контейнеры адресуются префиксами: `project:<projectId>` и `window:<windowId>` (по стабильному id окна — номер уровня не уникален между проектами). Старые формы `'project'` и `level-window-<N>` продолжают распознаваться и означают контейнеры активного проекта.

**Классы выделения взаимоисключающи.** В `selectedIds` лежат либо только контейнеры, либо только сущности графа: добавление элемента другого класса ЗАМЕНЯЕТ выделение. Благодаря этому `DELETE_SELECTED` всегда однозначен — он либо удаляет контейнеры (проекты целиком, уровни сверху вниз одним шагом истории), либо сущности.

#### Пакетная история

| Экшен | Payload | Описание |
|---|---|---|
| `BEGIN_HISTORY_BATCH` | `{ logMessage? }` | Открыть пакет: последующие экшены НЕ пишут свои шаги в историю |
| `COMMIT_HISTORY` | `{ snapshot?, logMessage? }` | Закрыть пакет одним шагом Undo |
| `CANCEL_HISTORY_BATCH` | — | Закрыть пакет без записи (аварийный выход) |

Серия экшенов от ИИ применяется именно так: весь ответ ассистента — **один** шаг Undo. Без этого батч из 30+ команд вымывал лимит истории в 20 шагов, и отменить работу ассистента было невозможно.

### 6. Ключевые инварианты при генерации портов и связей:

1. **Порты ОБЯЗАТЕЛЬНЫ:** Нейросеть должна самостоятельно генерировать порты (`ADD_PORT`) для узлов, задавая им подписи `name`, тип `input`/`output`, грань `edge` (`left`, `right`, `top`, `bottom`) и HEX-цвет.
2. **Связи соединяют ТОЛЬКО Порты:** Экшен `ADD_LINK` принимает в `sourcePortId` и `targetPortId` **строго ID ранее созданных портов**, а не ID узлов.
3. **Авто-выравнивание элементов на слое:** Координаты нод на слое следует разносить по сетке (`{x: 30, y: 80}`, `{x: 310, y: 80}`). При добавлении узлов приложение автоматически применяет к слою выравнивание `GeometryUtils.getSmartPlacement`.

   *Команда должна завершаться с нулевым кодом ошибки.*

## 📌 Памятка для ИИ по стилю внесения правок

* **Не нарушать работу Zero-Build:** Не использовать `require()` или `import` в браузерных React-компонентах.
* **Редьюсер не вызывает сам себя:** рекурсивный вызов `reducer(...)` внутри `const reducer = ...` ломает загрузку через babel-standalone (top-level `const` перестаёт быть виден другим скриптам). Общую логику выносить в top-level функции (пример: `applyRemoveLevelWindow`).
* **Кэш скриптов:** после правок компонентов поднимать метку версии `?v=...` у всех script-тегов в `app/index.html` — иначе браузер пользователя исполняет старый код.
* **Видимость сущностей** проверять ТОЛЬКО через `HierarchyUtils.isEntityVisible(id, state)` — единая точка истины для глобального (L0) и локальных «глаз». Не дублировать логику фильтрации в компонентах.
* **Цель создания элементов** («+», перетаскивание связи в окно) определять через `HierarchyUtils.getAddContext(state)`; при `ok:false` действие запрещено (массовое выделение или неоднозначная ветка).
* **Подписки на DOM-узлы условного рендера** (например, вьюпорт окна уровня, размонтируемый при сворачивании) вешать через callback-ref, а не `useEffect` с deps — слушатель должен следовать за жизненным циклом узла.
* **Использовать GitHub Flavored Markdown links:** При ответах пользователю создавать кликабельные ссылки на файлы вида `[basename](file:///absolute/path/to/file)`.
* **Сохранять docstrings и комментарии:** Не удалять существующие комментарии, описывающие бизнес-логику и математику выталкивания.
* **Использовать атомарные edits:** При правках файлов использовать точечную замену `replace_file_content` или `multi_replace_file_content`.
